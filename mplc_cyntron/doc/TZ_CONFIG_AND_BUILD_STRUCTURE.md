# Техническое задание: единый config.h и сборка под модули расширения

**Версия ТЗ:** 1.0  
**Дата:** 2025-02-11  
**Цель:** изменить структуру проекта и способ сборки так, чтобы один репозиторий содержал общую базу (драйверы, ядро, Modbus), а прошивка собиралась под каждое устройство (модуль расширения) отдельно, с включением только необходимых блоков кода и минимальным размером образа.

---

## 1. Цели и ограничения

### 1.1 Цели

1. **Один проект для всех модулей расширения** — общая кодовая база: ядро, драйверы (MCP23S17, AD5324, ADS1220, ATM90E32 и т.д.), Modbus, приложение, реестр модулей. Никакого копирования проекта под каждый вариант устройства.

2. **Единая точка конфигурации** — файл `config.h`, подключаемый везде, в котором задаются:
   - отличия одной модели/ревизии устройства от другой (ревизия платы, пины, варианты);
   - набор модулей расширения для данной сборки;
   - при необходимости — опции периферии и отладки.

3. **Условная компиляция по конфигу** — этим файлом определяется:
   - какие **исходные файлы** участвуют в сборке (какие реализации модулей и при необходимости какие драйверы компилировать);
   - какие **модули** регистрируются в реестре и доступны в прошивке;
   - какие **блоки кода** внутри общих файлов включаются (`#ifdef` по макросам из config.h).

4. **Уменьшение размера прошивки** — для каждой сборки (под конкретный модуль или набор модулей) в образ попадает только код, необходимый для выбранных модулей и ревизии платы, без кода неиспользуемых модулей и по возможности без неиспользуемых драйверов.

### 1.2 Ограничения

- Совместимость с существующим функционалом: поведение устройств по Modbus, работа бутлоадера, обновление прошивки не должны измениться с точки зрения пользователя.
- Сохранение возможности сборки в STM32CubeIDE (или явный переход на другую систему сборки с обоснованием).
- Конфигурация должна быть пригодна для CI: сборка разных вариантов одной командой или по одному описанию (например, список целей в Makefile/CMake).

## 2. Текущее состояние (кратко)

- **Конфигурация:** в `Core/Inc/main.h` заданы `HARDWARE_MP` (20/21/22), переопределения пинов под ревизию, макросы `INCLUDE_DO6DI8`, `INCLUDE_AO6AI6`, … (включение модулей). Регистрация модулей и условная компиляция в коде опираются на эти макросы.
- **Сборка:** в проект (`.cproject`) входят все исходники из `Core` и `Modules` (исключения только по путям: например `periph/adc/ADS1120.cpp`, подпапки nanoMODBUS). Все реализации модулей (`module_do6.c`, `module_ai12.c`, …) компилируются в одну прошивку; выбор «какой модуль активен» — только в рантайме (определение по GPIO, переключение активного модуля в реестре). Размер образа не зависит от набора модулей.
- **Модули расширения** (идентификаторы и номера по README):

  - DO16 (2) — 16ДО SSR, MCP23S17

  - DI14 (5) — 14ДИ, MCP23S17  
  - AO6AI6 (6) — 6АО 6АИ, AD5324 + ADS1220/MUX/AI  
  - AI12 (7) — 12АИ, ADS1220/MUX

## 3. Требования к config.h

### 3.1 Назначение и место

- **Единственный** файл конфигурации устройства/сборки для всего проекта (ядро, модули, драйверы, приложение).
- **Расположение:** `Core/Inc/config.h` (или альтернативно `config/config.h` в корне с добавлением пути include; в ТЗ далее — `Core/Inc/config.h`).
- **Подключение:** подключается **первым** (или сразу после системных/стандартных заголовков) во всех исходниках, где нужна конфигурация. Рекомендуемый порядок: в `main.h` в блоке «Private includes» первая строка — `#include "config.h"`; остальные файлы проекта подключают конфигурацию через `main.h` либо напрямую `#include "config.h"`, чтобы везде были видны одни и те же макросы.

### 3.2 Содержимое config.h

Файл должен задавать и документировать следующее.

#### 3.2.1 Ревизия платы (аппаратная)

- **Макрос ревизии:** `HARDWARE_MP` со значением 20, 21 или 22 (и при необходимости последующие).
- **Назначение:** выбор пинов, вариантов инициализации (кнопка, светодиоды, SPI_CS и т.д.), условная компиляция в `gpio_hal.c`, `module_do6.c` и других файлах, где есть ветвление по ревизии.
- **Пример:** для ревизии 21 — переопределение `BUTTON_Pin`, `BOT_LED_9_Pin`, `TOP_LED_9_Pin` и портов (как сейчас в `main.h`). Все такие переопределения переносятся в `config.h` или в подключаемый из него файл (например `config_board_mp02m.h`).

#### 3.2.2 Набор модулей расширения для данной сборки

- **Макросы включения модулей:** для каждого модуля расширения — один макрос вида `INCLUDE_<MODULE>`, например:
  - `INCLUDE_DO6DI8`, `INCLUDE_DO16`, `INCLUDE_AO12`, `INCLUDE_DO6`, `INCLUDE_DI14`, `INCLUDE_DO4DI6`;
  - `INCLUDE_AO6AI6`, `INCLUDE_AI12`, `INCLUDE_EN_METER`, `INCLUDE_TENZO2`.
- **Правило:** если для данной сборки модуль не нужен, соответствующий `INCLUDE_*` не определяется (или закомментирован). Код и реестр модулей по существующей схеме используют `#ifdef INCLUDE_*` для условной компиляции и регистрации только включённых модулей.

#### 3.2.3 Опции периферии и отладки (по необходимости)

- Режимы SPI/Modbus (например `SPI1_MODE`, `MODBUS_MODE`), если их решено вынести из `main.h` в конфиг.
- Опциональные отладочные макросы (например `COM_PORT_DEBUG`, `NMBS_DEBUG`), если они должны задаваться из одного места для всей сборки.

#### 3.2.4 Запрет дублирования конфигурации

- В `main.h` (и в остальных заголовках) не должно оставаться дублирующих определений ревизии платы и набора `INCLUDE_*`; они задаются **только** в `config.h`. В `main.h` допускается только `#include "config.h"` и, при необходимости, обратная совместимость через `#ifndef HARDWARE_MP` с дефолтом (с явной пометкой в комментарии).

### 3.3 Варианты использования config.h

- **Вариант A (один config.h в репозитории):** в репозитории лежит один файл `config.h` с выбранным по умолчанию набором модулей и ревизией; для другой сборки конфиг меняют вручную или скриптом перед сборкой.
- **Вариант B (несколько файлов конфигурации):** в репозитории несколько файлов, например `config_do6di8.h`, `config_ai12.h`, `config_ao6ai6.h`, каждый определяет свой набор `INCLUDE_*` и при необходимости свою ревизию; при сборке в систему сборки передаётся имя конфига (например через `-DCONFIG_FILE=config_do6di8.h` и `#include CONFIG_FILE` в общем заголовке) или копирование выбранного файла в `config.h`.
- **Вариант C (генерируемый config.h):** скрипт или система сборки по целевому имени (например `make TARGET=DO6DI8`) генерирует `config.h` из шаблона.  

ТЗ не фиксирует единственный вариант; при реализации выбирается один подход и отражается в разделе «Реализация» и в README.

## 4. Требования к составу сборки (какие файлы компилируются)

### 4.1 Обязательные для любой прошивки

- Ядро: `main.c`, `system_stm32f0xx.c`, `stm32f0xx_it.c`, инициализация HAL/MSP, кнопка, таймеры, DMA, SPI, USART, I2C и т.д. — всё, что не зависит от набора модулей.
- Общие модули: `module_registry.c`, `module_registry.h`, интерфейсы модулей (`module_interface.h`, `module_registry.h`).
- Modbus: стек nanoMODBUS, `modbus_rtu_hw.c`, `fast_mb.c`, `fast_mb_events.c`, `fast_mp_port.c` и т.д.
- Система: таймер, индикация, кнопка, отладка, EEPROM — в объёме, необходимом для работы выбранных модулей.
- Драйверы, которые используются **хотя бы одним** включённым модулем (см. п. 4.2).

### 4.2 Условная компиляция по модулям

- **Реализации модулей** (`Core/modules/implementations/module_*.c`): в сборку включаются **только** те файлы, для которых в `config.h` определён соответствующий `INCLUDE_*`:
  - `INCLUDE_DO6DI8` → `module_do6di8.c`;
  - `INCLUDE_DO16` → `module_do16.c`;
  - `INCLUDE_AO12` → `module_ao12.c`;
  - `INCLUDE_DO6` → `module_do6.c`;
  - `INCLUDE_DI14` → `module_di14.c`;
  - `INCLUDE_DO4DI6` → `module_do4di6.c`;
  - `INCLUDE_AO6AI6` → `module_ao6ai6.c`;
  - `INCLUDE_AI12` → `module_ai12.c`;
  - `INCLUDE_EN_METER` → `module_en_meter.c`;
  - `INCLUDE_TENZO2` → `module_tenzo2.c`.

- **Драйверы и подсистемы, привязанные к модулям** (включать в сборку только если нужен хотя бы один модуль, их использующий):
  - MCP23S17: используется DO6DI8, DO16, DO6, DI14, DO4DI6, AO6AI6 (частично), AI12 (частично). Если ни один из этих модулей не включён — файлы драйвера MCP23S17 можно исключить из сборки (при условии, что остальной код не ссылается на них).
  - AD5324 (ad53x4): AO12, AO6AI6. Исключать из сборки, если нет INCLUDE_AO12 и INCLUDE_AO6AI6.
  - ADS1220, MUX, AI-каналы (ads1220_c, mux_c, ai_channel_*, adc_worker_task_c, таблицы термопар/NTC/PT и т.д.): AO6AI6, AI12. Исключать, если нет INCLUDE_AO6AI6 и INCLUDE_AI12.
  - ATM90E32: EN_METER. Исключать, если нет INCLUDE_EN_METER.

Таблица зависимостей «модуль → исходные файлы и драйверы» для текущего набора модулей приведена в приложении A; её актуальная версия должна храниться в проекте (например в `doc/CONFIG_BUILD_MATRIX.md`) и обновляться при добавлении новых модулей.

### 4.3 Исключение исходников на этапе сборки

- Система сборки (Makefile, CMake или конфигурации .cproject) должна **не компилировать** файлы, не входящие в выбранный состав (см. п. 4.1–4.2).  
- Не допускается полагаться только на то, что неиспользуемый код «отрежется линкером»: неиспользуемые реализации модулей и по возможности неиспользуемые драйверы **не должны передаваться компилятору** как цели сборки. Это обеспечивает предсказуемое уменьшение размера прошивки и времени сборки.

## 5. Требования к системе сборки

### 5.1 Зависимость от config.h

- Состав компилируемых исходных файлов определяется конфигурацией сборки, которая **соответствует** выбранному `config.h`:
  - либо при сборке используется один фиксированный `config.h` (например из репозитория или сгенерированный перед сборкой);
  - либо у сборки есть несколько целей (конфигураций), и для каждой цели заданы свои макросы (`-DINCLUDE_DO6DI8`, `-DINCLUDE_AI12`, …) и свой список исходников, **согласованный** с описанным в п. 4.

- Предкомпиляционная проверка: при наличии инструмента (скрипт, этап в Make/CMake) рекомендуется проверять, что набор скомпилированных модулей совпадает с набором `INCLUDE_*` из config.h (или из флагов сборки), и при расхождении выдавать ошибку.

### 5.2 Варианты реализации системы сборки

- **Вариант 1 — Makefile:** корневой или в `Core/` Makefile формирует список `C_SRCS` в зависимости от конфига (чтение config.h или переменная цели, например `TARGET=DO6DI8`). Сборка одной целью собирает одну прошивку с одним набором модулей.
- **Вариант 2 — CMake:** переменная или список модулей (соответствующий config) задаётся при конфигурации (например `cmake -DMODULES=DO6DI8;DO6`); в CMakeLists.txt по этому списку формируются источники и добавляются определения `INCLUDE_*`.
- **Вариант 3 — STM32CubeIDE (.cproject):** для каждой целевой прошивки (например «MP-02m DO6DI8», «MP-02m AI12») создаётся отдельная конфигурация сборки (Build Configuration). В каждой конфигурации заданы свои Define symbols (`-DINCLUDE_DO6DI8` и т.д.) и свой список исключённых из сборки исходников (exclude resource), так что компилируются только нужные `module_*.c` и при необходимости исключаются ненужные драйверы. Файл `config.h` может генерироваться пребилд-шагом из шаблона по выбранной конфигурации или содержать только общую часть, а набор модулей задаётся макросами из настроек сборки.

Один из вариантов выбирается и реализуется; в ТЗ зафиксировать выбранный вариант и шаги воспроизведения сборки для каждой цели.

### 5.3 Именование артефактов и целей

- Рекомендуется единый формат имени прошивки/цели, например: `mp-02m-<модуль>.elf` / `mp-02m-<модуль>.bin` (например `mp-02m-do6di8.elf`) или `mp-02m-<ревизия>-<модуль>.bin`. Для сборки «все модули» (как сейчас) — отдельное имя, например `mp-02m-all.elf`. Точный формат зафиксировать в проекте.

## 6. Структура проекта после изменений

### 6.1 Рекомендуемое размещение

- `Core/Inc/config.h` — основной конфигурационный файл (ревизия платы, набор модулей, опции).
- При варианте с несколькими конфигами: `Core/Inc/config/config_do6di8.h`, `config_ai12.h` и т.д., либо `config/config_*.h` в корне проекта.
- `main.h` подключает `config.h` в начале и больше не дублирует определения ревизии и `INCLUDE_*`; при необходимости оставляет только обратную совместимость и комментарии.
- Документация по соответствию «модуль — файлы — драйверы»: в `doc/` (например `CONFIG_BUILD_MATRIX.md` или раздел в существующем документе).

### 6.2 Зависимости включений

- Порядок: в каждом исходном файле, где нужна конфигурация, сначала подключается конфиг (напрямую или через `main.h`). Заголовки модулей и драйверов могут подключать только `config.h` или `main.h`, не дублируя логику выбора модулей.

## 7. Этапы внедрения (план работ)

1. **Введение config.h и перенос настроек**
   - Создать `Core/Inc/config.h`.
   - Перенести из `main.h` в `config.h`: `HARDWARE_MP`, все переопределения пинов по ревизии, все `INCLUDE_*`.
   - В `main.h` оставить `#include "config.h"` и убрать перенесённые определения; при необходимости добавить `#ifndef HARDWARE_MP` с дефолтом.
   - Убедиться, что во всех затронутых файлах конфигурация доступна через уже подключаемый `main.h` или добавить `#include "config.h"` там, где он нужен и main.h не подключается.

2. **Фиксация состава сборки по модулям**
   - Составить таблицу: модуль → список исходных файлов (реализация модуля + используемые драйверы/подсистемы). Оформить в `doc/CONFIG_BUILD_MATRIX.md` (или аналог).
   - Зафиксировать правила: при каких `INCLUDE_*` компилируются какие `module_*.c` и какие драйверы (mcp23s17, ad53x4, ads1220_c, mux_c, ai_channel_*, atm90e32 и т.д.).

3. **Изменение системы сборки**
   - Реализовать выбранный вариант (Makefile / CMake / несколько конфигураций .cproject) так, чтобы состав компилируемых файлов зависел от конфигурации (config.h или эквивалентных макросов).
   - Для каждой целевой прошивки (каждый модуль или выбранные комбинации) обеспечить сборку без включения лишних `module_*.c` и по возможности без лишних драйверов.
   - Проверить сборку всех вариантов (как минимум по одному на каждый модуль и вариант «все модули»).

4. **Проверка размера и поведения**
   - Сравнить размер образа для сборки «один модуль» (например только DO6DI8) с текущей сборкой «все модули»; зафиксировать выигрыш по размеру.
   - Убедиться, что функционал выбранного модуля (Modbus, реле, АИ, АО, счётчик и т.д.) не изменился; при необходимости провести регрессионные проверки по чек-листам.

5. **Документация и CI**
   - Обновить README и при необходимости `doc/BOOTLOADER_INTEGRATION.md`: как собирать прошивку под конкретный модуль, как задаётся config, где лежит таблица модуль–файлы.
   - Если используется CI: добавить сборку нескольких целей (например DO6DI8, AI12, AO6AI6) и публикацию артефактов с понятными именами.

## 8. Критерии приёмки

- Существует единый файл конфигурации `config.h` (или эквивалентный механизм с несколькими файлами/генерацией), подключаемый во всех нужных местах и содержащий отличия ревизий и набор модулей расширения.
- Набор модулей расширения и ревизия платы задаются только в config.h (или через макросы сборки, согласованные с config.h); дублирования в main.h нет.
- Система сборки формирует состав компилируемых файлов в зависимости от конфигурации; для сборки «один модуль» не компилируются реализации остальных модулей.
- Размер прошивки для сборки с одним модулем меньше размера прошивки «все модули» при той же оптимизации и целевом чипе.
- Сборка всех заявленных вариантов (по списку целей в документации) выполняется без ошибок; артефакты имеют предсказуемые имена.
- Документация описывает: расположение config.h, способ выбора конфигурации, соответствие модуль–файлы, команды/шаги для сборки под конкретный модуль.

## 9. Глоссарий и ссылки

- **Модуль расширения** — вариант устройства MP-02m (мезонина): 6ДО8ДИ, 12АИ, 6АО6АИ и т.д.; идентифицируется типом `mp02_t` и макросом `INCLUDE_*`.
- **Ревизия платы** — аппаратная версия базовой платы (HARDWARE_MP 20/21/22), определяет пины и варианты инициализации.
- **config.h** — единый заголовочный файл конфигурации сборки/устройства.

**Общие файлы** (входят во все сборки, если не решено выносить за условную компиляцию): module_registry.c, modbus_rtu_hw.c, fast_mb*.c, gpio_hal.c (с ветвлением по INCLUDE_* внутри), main.c, app_c.c, system_timer.c, debug_output.c, eeprom_manager, button_handler, light_indicator, драйверы HAL, startup.

При исключении из сборки модулей AO6AI6 и AI12 можно не компилировать: ads1220_c.c, mux_c.c, ai_channel_*.c, adc_worker_task_c.c, таблицы (table_*.c). Точный минимальный список файлов по каждой цели уточняется при реализации и заносится в doc/CONFIG_BUILD_MATRIX.md.
