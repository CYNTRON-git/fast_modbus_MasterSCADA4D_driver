# Несоответствия: test (рабочий бутлоадер/прошивальщик) и текущий проект

Сравнение папки **test** (рабочий бутлоадер и прошивальщик с broadcast по адресу 0) и текущего проекта (broadcast 255).

---

## 1. Адрес broadcast

| Место | test | Текущий проект |
|-------|------|----------------|
| **Бутлоадер** | **0** (0x00). В `main.c`: `rx[0] != 0U`, `rx[0] == 0U`; в `modbus_bl.c`: `req_addr == 0`. В `bootloader_config.h`: «Ответ на адрес 0x00 (broadcast)». | **255** (0xFF). В `main.c`: `rx[0] != 0xFFU`, `rx[0] == 0xFFU`; в `modbus_bl.c`: `req_addr == 0xFFU`. В `bootloader_config.h`: «только 0xFF/255». |
| **Прошивальщик (modbus_rtu.py)** | В репозитории: `BROADCAST_ADDR = 0xFF` (255). То есть в test флашер по коду тоже 255; для работы с тестовым бутлоадером (0) нужен broadcast 0. | `BROADCAST_ADDR = 0xFF` (255). |
| **Основное приложение (Modbus)** | В test: `modbus.h` задаёт `NMBS_BROADCAST_ADDRESS = 0xFF`; в `Modules/nanoMODBUS/nanomodbus.h` по умолчанию **0**. Итог зависит от того, какой заголовок линкуется. | `Core/modbus/inc/modbus.h`: `NMBS_BROADCAST_ADDRESS = 0xFF`. |

**Итог:** В test бутлоадер рассчитан на **broadcast = 0**. Текущий бутлоадер и флашер используют **255**. Чтобы текущий проект работал как test (broadcast 0), в бутлоадере и во флашере нужно использовать адрес 0 (через конфиг/константу).

---

## 2. Причина разницы 0 и 255

В текущем проекте и в части test (основное приложение) выбран **255**, чтобы искажённый первый байт **0x00** на линии не воспринимался как broadcast и не переводил все устройства в бутлоадер. См. `doc/HANG_AND_ERROR_CAUSES_ANALYSIS.md`, `doc/BOOTLOADER_ENTRY_AND_BROADCAST.md`.

В test бутлоадер использует **0** как broadcast — это совпадает с классическим Modbus (адрес 0 = broadcast). С таким бутлоадером должен работать флашер с `BROADCAST_ADDR = 0`.

---

## 3. Другие отличия test vs текущий проект

| Аспект | test | Текущий проект |
|--------|------|----------------|
| Логика «сначала адрес приложения» во флашере | В test `app_gui.py`: после перевода в бутлоадер сначала опрос по адресу приложения, при таймауте — broadcast. | В текущем: после перевода в бутлоадер сразу broadcast (или сканирование), без опроса по адресу приложения. |
| Задержка между блоками прошивки | Нужно проверить в test (flash_protocol.py). | 50 мс после каждого блока (чтобы бутлоадер успевал записать Flash). |
| Регистр причины отказа info-блока (0xF1) | В test бутлоадере может не быть. | Есть: чтение 0xF1 после исключения 04. |
| Лимит размера образа | Нужно проверить. | 228864 байт (0x08038000 − 0x0800800). |
| Сигнатура EEPROM (пробел = 0) | В test бутлоадере: `sig_eeprom[i] != 0xFF && sig_eeprom[i] != sig_in[i]` (без нормализации 0x20). | Нормализация 0x20 ↔ 0 при сравнении сигнатуры. |

---

## 4. Текущий проект: только 255

- **Основное приложение, бутлоадер, флашер:** broadcast только **255** (0 не поддерживается).
- Совместимость с test (broadcast 0) в текущем дереве не предусмотрена.
