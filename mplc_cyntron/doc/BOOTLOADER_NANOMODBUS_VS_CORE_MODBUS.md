# Бутлоадер: почему используется своя копия nanoMODBUS, а не Core/modbus

**Примечание:** Папка `Modules/nanoMODBUS` удалена из проекта. Основное приложение использует только **Core/modbus** (включать `modbus.h` из Core/Inc). Бутлоадер по-прежнему использует локальную копию в `bootloader/Core/Inc` и `bootloader/Core/Src`.

## Ситуация

В проекте два варианта Modbus-библиотеки с совместимым API (nmbs_t, nmbs_server_create, nmbs_server_poll, callbacks):

- **Локальная копия в бутлоадере** (`bootloader/Core/Inc/modbus.h`, `bootloader/Core/Src/modbus.c`) — используется при сборке бутлоадера (эталон — папка `2`).
- **Core/modbus** — для **основного приложения**: Fast Modbus, арбитраж, DMA, интеграция с modbus_rtu_hw.

При сборке бутлоадера с **Core/modbus** (подключение `modbus.h` и линковка `Core/modbus/src/modbus.c`) прошивка приложения приводила к **перезагрузке бутлоадера** во время записи блоков. После перехода на локальную копию nanoMODBUS в бутлоадере прошивка работает стабильно.

## В чём была проблема с Core/modbus

1. **Разное назначение кода**
   - Core/modbus рассчитан на основное приложение: DMA, таймеры, Fast Modbus, арбитраж. В бутлоадере используется только простой сценарий: один кадр уже в буфере → `nmbs_server_poll` → callback → ответ.
   - Подключение Core/modbus тянет за собой ту же кодовую базу, что и в приложении, но без полного контекста (другие объекты, другой Makefile). Риск расхождений в поведении и лишнего кода выше.

2. **Отличия в константах**
   - В **Core/modbus** (inc/modbus.h): `NMBS_BROADCAST_ADDRESS = 0xFF` (255), в комментарии указано «0 не поддерживается».
   - В оригинальном nanoMODBUS: `NMBS_BROADCAST_ADDRESS = 0`.
   - В бутлоадере broadcast обрабатывается в `main.c` через `modbus_bl_process` (проверка `rx[0] == BL_BROADCAST_ADDR`), запросы на broadcast в `nmbs_server_poll` не попадают. Для единообразия с эталоном и прошивальщиком в бутлоадере используется **BL_BROADCAST_ADDR 255** и локальная копия библиотеки.

3. **Сборка и зависимости**
   - При использовании Core/modbus в Makefile бутлоадера были: `-flto`, линковка `sysmem.o`. LTO мог влиять на порядок/размер кода в глубокой цепочке (callback → `process_data_block_sync` → ram_flash). `sysmem` (sbrk) бутлоадеру не нужен.
   - Сборка с локальной копией nanoMODBUS совпадает с эталоном (папка `2`): без `-flto`, без `sysmem.o`, только нужные объекты — поведение и размер образа предсказуемы.

4. **Соответствие эталону**
   - Рабочий эталон бутлоадера (папка `2`) собирается с той же логикой. Чтобы основной бутлоадер в корне проекта вёл себя так же и прошивка не падала, он должен использовать локальную копию и тот же сценарий (запись блока в callback до ACK, как в эталоне).

## Вывод

- В бутлоадере используется локальная копия в **bootloader/Core/Inc** и **bootloader/Core/Src** (`modbus.h`, `modbus.c`).
- **Core/modbus** оставить только для основного приложения (Modbus по DMA, Fast Modbus и т.д.).
- В `bootloader/Core/Src/modbus_bl_nmbs.c` — `#include "modbus.h"`. В Makefile бутлоадера: сборка `bootloader/Core/Src/modbus.c`, include `-I$(TOP)/bootloader/Core/Inc`.
