# Отличия прошивальщика Wiren Board (wb-mcu-fw-updater) от нашего

Источники: репозиторий wirenboard/wb-mcu-fw-updater (fw_flasher.py, wb_modbus/bindings.py).

## Уже приведено к их поведению

1. **Info-блок (0x1000)**  
   Первые 32 байта файла отправляются как 16 регистров **Big-Endian** (байт 0 = старший байт слова). Мы так делаем и для .wbfw, и для .fw.

2. **Таймаут при отправке info-блока (WB)**  
   Для записи 0x1000 при прошивке WB используется увеличенный таймаут: `max(INFO_RESPONSE_TIMEOUT_MS, BOOTLOADER_INFOBLOCK_TIMEOUT_MS_WB)` (в app_gui; константа 3 с в flash_protocol).

3. **Порядок байт в блоках данных WB (0x2000)**  
   Блоки по 136 байт отправляются как 68 регистров **Big-Endian** (как в wb-mcu-fw-updater), см. `payload_block_to_registers_wb`.

4. **Регистры загрузчика WB 1000/1001/1003**  
   Добавлены константы `REG_WB_UART_RESET`, `REG_WB_EEPROM_ERASE`, `REG_WB_FREE_SPACE`. Перед прошивкой WB опционально читается рег. 1003 (свободное место FlashFS); значение и предупреждение при нехватке места выводятся в лог.

5. **Наша конфигурация и окружение (п.8)**  
   См. раздел «Наша конфигурация» ниже.

## Наша конфигурация (прошивальщик и прошивки)

- **Платформа:** Windows (GUI приложение).
- **Источник прошивок:** локальные файлы (.fw, .bin, .wbfw); ручной выбор файла и устройства.
- **Нет:** автообновления прошивок с сервера, wb-mqtt-serial, Linux/серверного сценария.
- **Обмен:** RS-485/COM, ручной выбор порта и параметров; сканирование устройств (в т.ч. WB extended 0xFD 0x46 0x01); прошивка по Modbus-адресу или по серийному номеру (0xFD 0x46 0x08).

## Приведено к полному соответствию (наши устройства и WB)

### 3. Повтор при ошибке блока

- **У них (flasher.c):** до 3 попыток на блок; после 3 неудач — пропуск блока; при 6 подряд ошибках — выход.
- **У нас:** тот же алгоритм для **наших устройств** и для **WB**: 3 попытки на блок (`APP_MAX_ERROR_COUNT`), пропуск при 3 неудачах, выход при 6 подряд (`APP_EXIT_CONSECUTIVE_ERRORS`).

### 4. Задержка между блоками

- **У них:** только `interFrameDelay()` (sleep(0)) между кадрами.
- **У нас:** по адресу — 5 мс (`BLOCK_DELAY_AFTER_RESPONSE_S`); по серийному 0x46 (быстрый Modbus) — **0 с**, как у WB (`BLOCK_DELAY_*_S_FAST = 0` в `run_flash_sequence`).

### 5. Таймаут ответа загрузчика

- **У них:** BL_MINIMAL_RESPONSE_TIMEOUT 5 с.
- **У нас:** 5 с для записи 0x2000 и для WB, и для наших устройств (`BOOTLOADER_DATA_BLOCK_TIMEOUT_MS`).

### 6. Прошивка по серийному: обнаружение загрузчика и скорость

- **Проблема 1:** после перехода в бутлоадер серийный номер загрузчика может отличаться от серийного приложения (EEPROM/Flash). Поэтому после открытия порта выполняется **WB extended scan (0xFD 0x46 0x01)**; полученный серийный используется для обмена 0xFD 0x46 0x08 (app_gui: при `use_fast_modbus` перед `read_bootloader_info_by_serial`).
- **Проблема 2:** ответ бутлоадера в обёртке 0xFD 0x46 0x09 содержит **inner PDU без байта адреса** (5 байт для 0x10/0x06). Ранний выход в `send_receive` считал длину кадра неверно (ожидал 19 байт вместо 14) и уходил в таймаут 5 с на каждый блок. Исправлено в serial_port.py: заголовок 7 байт, inner_len=5 для 0x10/0x06, выход при `len >= 7+inner_len+2`. Прошивка по серийному по времени приближается к прошивке по адресу (~50 с вместо ~600 с).

### 7. Повтор info-блока при таймауте

- **У них:** при ошибке info — до 3 повторов с sleep(3).
- **У нас:** 3 повтора с паузой 3 с (`INFO_RETRY_SLEEP_S`) для наших устройств и для WB.

### 8. Размер блока данных

- **WB:** 136 B (68 рег) в 0x2000.
- **Наши устройства:** 246 B (123 reg) в 0x2000.
- Порядок байт: WB — BE на линии; наши .fw — регистр как (мл.байт<<8)|ст.байт, чтобы в Flash получился LE.

## Отличия, которые остаются

---

### 9. Переход в приложение после прошивки (WB)

- **У них:** в `ModbusFlasher.flash()` только `_send_info` и `_send_data`; записи в рег. 1004 (jump to app) в этом методе нет. Переход, видимо, делается выше по коду или вручную.
- **У нас:** после успешной прошивки WB отправляем `write_multiple_registers(..., REG_JUMP_APP, [1])`.

Мы явно переводим устройство в приложение — это удобнее для пользователя.

---

### 10. Дополнительные команды загрузчика (WB)

- **У них:** рег. 1000 (UART reset), 1001 (EEPROM erase), 1003 (get free space FlashFS) используются для сброса и проверки места.
- **У нас (прошивальщик):** константы 1000/1001/1003; перед прошивкой WB — опциональный опрос рег. 1003 и вывод в лог.
- **У нас (прошивка приложения):** реализованы в приложении MP-02m (Modbus): **1000** — запись 1 → переинициализация UART RS-485 с текущими параметрами из EEPROM (`set_reload_rs485()`); **1001** — запись 1 → отложенный сброс на заводские настройки (`load_default_config()` в main loop); **1003** — чтение → свободное место EEPROM в байтах (один регистр, до 0xFFFF).

---

### 10. Толерантность к стоп-битам (WB)

- **У них:** используется `StopbitsTolerantInstrument`: при приёме ответа временно переключают стоп-биты на 1 (часть устройств WB так отвечает при 8N2).
- **У нас:** фиксированные 9600 8N2 для обмена с загрузчиком WB.

Если на части устройств ответы при 8N2 нестабильны, имеет смысл рассмотреть аналог их приёма (смена стоп-бит только на время чтения ответа).

---

### 11. Конфигурация и окружение

- **У них:** Linux, конфиг, wb-mqtt-serial, скачивание прошивок с сервера, автообновление.
- **У нас:** см. раздел «Наша конфигурация» выше (Windows GUI, локальные файлы, ручной выбор).

## Алгоритм прошивки (совместимость с wb-mcu-fw-flasher)

**Наши устройства (.fw, по адресу или по серийному)** и **WB (.wbfw)** используют один и тот же алгоритм:

- **Info (0x1000):** 32 байта → 16 регистров BE. До 3 повторов при ошибке/таймауте с паузой 3 с. После успеха — пауза (наши: 3 с — стирание региона; WB: 0 с).
- **Data (0x2000):** между блоками задержка 0 с. Таймаут ответа загрузчика 5 с. При ошибке блока: 3 попытки → при 3 неудачах пропуск блока; при 6 подряд ошибках — выход.
- **Размер блока:** наши — 246 B (123 рег), WB — 136 B (68 рег). Порядок байт: у нас для .fw — LE в Flash; у WB — BE на линии.
- **Переход в приложение:** после успешной прошивки отправляем запись в рег. 1004 (jump to app).
