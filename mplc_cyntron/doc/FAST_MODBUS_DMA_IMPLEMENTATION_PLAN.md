# Быстрый Modbus (0xFD, 0x46/0x60) в режиме DMA — план реализации

## Как сейчас работает устройство (режим DMA)

| Тип запроса | Адрес / формат | Поведение |
|-------------|----------------|-----------|
| **Обычный Modbus RTU** | Адрес 1…247 (наш адрес), функции 0x01–0x10 и т.д. | Кадр принимается по DMA (IDLE/RTO). В `HAL_UARTEx_RxEventCallback` вызывается `nmbs_server_poll()` → формируется ответ → отправка через `MB_SendFrame` (DMA TX) → `MB_RecieveFrame()` перезапускает приём. **Работает.** |
| **Broadcast** | Адрес 255 | Кадр принимается; если `modbus_rtu_broadcast_allowed()` — запрос откладывается (слот addr×3 мс), в main выполняется `rtu_broadcast_process_pending()`: poll и ответ по DMA, затем `MB_RecieveFrame()`. **Работает.** |
| **Быстрый Modbus** | 0xFD, 0x46/0x60 (сканирование/события) | Кадр принимается; при `buf[0]==0xFD` сразу вызывается только `MB_RecieveFrame()` — кадр не разбирается, ответ не формируется. Устройство **молча игнорирует** запросы быстрого Modbus (хост не получит ответ). |
| **Чужой адрес** | Адрес ≠ наш и ≠ 255 и ≠ 0xFD | Кадр принимается, не обрабатывается, приём перезапускается. **Корректно.** |

Итого: при одновременном использовании обычного и быстрого Modbus в режиме DMA обычные запросы и broadcast обрабатываются, запросы по быстрому Modbus (0xFD) — нет (устройство на них не отвечает).

---

## Можно ли реализовать

**Да.** Протокол быстрого Modbus в текущей реализации состоит из двух частей:

1. **Вход (определение команды)** — по приходу кадра 0xFD проверяется CRC и подкоманда (0x01 begin_scan, 0x02 next_scan, 0x05 poll_events и т.д.). В режиме IRQ это делается по байтам в `UART_RxCplt` при накоплении 5 байт; в DMA полный кадр уже есть в буфере — достаточно один раз вызвать тот же разбор по готовому кадру.

2. **Ответ (арбитраж и данные)** — полностью управляется **таймером TIM14**: окна арбитража (биты слова по одному), затем вызов `answer_scan` / `answer_events` / `end_scan` и отправка ответа через `write_serial` (в DMA — через `MB_SendFrame`). Приёма по байтам после старта таймера не требуется.

Итого: в DMA нужно (а) по полному кадру 0xFD один раз выполнить вход в автомат (аналог того, что в IRQ делается в `UART_RxCplt` по 5 байтам) и (б) обеспечить работу того же таймера и тех же функций ответа, с подменой только «перезапуск приёма» и «отправка» на DMA-варианты.

---

## Что нужно сделать

### 1. Общая логика (без режима)

- **Разбор кадра 0xFD**  
  Функция `check_fast_modbus(nmbs, length)` в `fast_mb.c` уже работает по готовому буферу `nmbs->msg.buf` и длине. Сейчас она используется только при `MODBUS_MODE_IRQ`. Нужно, чтобы её можно было вызывать и из пути DMA при полном кадре (например, из `HAL_UARTEx_RxEventCallback` при `buf[0]==0xFD` и `Size>=5`).

- **Таймер TIM14**  
  Вся логика арбитража и ответов в `Timer_FastModbus()` завязана только на таймер и `nmbs->msg` (режим, окно, слово арбитража и т.д.). Она не зависит от способа приёма (байт или кадр). Для DMA достаточно:
  - при приёме кадра 0xFD один раз выставить `nmbs->msg` (режим, `arbitrage_window`, `make_arbitrage_data` / `make_arbitrage_data_events`) и запустить TIM14 с нужным периодом (`MX_TIM_FastMB_Init(mode, &nmbs)` + `HAL_TIM_Base_Start_IT`);
  - в прерывании TIM14 по-прежнему вызывать `Timer_FastModbus(&nmbs)` (уже есть в `HAL_TIM_PeriodElapsedCallback`, но только при `MODBUS_MODE_IRQ` — нужно включить вызов и для DMA).

- **Отправка**  
  В быстром Modbus отправка идёт через `write_serial()` (в `fast_mp_port.c`), которая дергает `params->UART_Transmit`. В DMA отправка должна идти через `MB_SendFrame` (уже используется для обычного Modbus). То есть в DMA нужен путь, по которому код быстрого Modbus «пишет» кадр тем же интерфейсом, что и основной стек (например, вызов `MB_SendFrame` или общий callback отправки из `modbus_rtu_hw`).

- **Перезапуск приёма**  
  После завершения ответа быстрого Modbus в IRQ вызываются `nano_RecieveMode(nmbs)` или `fastmodbus_RecieveMode(nmbs)` (перезапуск приёма по байтам + таймер 3.5 символа). В DMA перезапуск приёма — это `MB_RecieveFrame()`. Нужна одна точка «перезапустить приём», которая в IRQ вызывает текущую логику, в DMA — `MB_RecieveFrame()`.

### 2. Изменения по файлам и режимам

| Задача | Где | Что сделать |
|--------|-----|-------------|
| Вызов разбора и входа в автомат по кадру 0xFD в DMA | `modbus_rtu_hw.c` (DMA, `HAL_UARTEx_RxEventCallback`) | При `buf[0]==0xFD` и `Size>=5`: `msg_buf_set(&nmbs, Size)`; вызвать разбор кадра (см. ниже); при `begin_scan`/`next_scan`/`poll_events` — установить `nmbs.msg.fast_mb_mode`, arbitrage data, инициализировать и запустить TIM14. Не вызывать `MB_RecieveFrame()` сразу — приём перезапустится по завершении быстрого Modbus. |
| Доступ к разбору 0xFD вне IRQ | `fast_mb.c` / заголовок | Сделать вызов `check_fast_modbus(nmbs, length)` возможным при `MODBUS_MODE_DMA`: вынести в общий код или снять условие `#if MODBUS_MODE_IRQ` с нужных частей (например, только `check_fast_modbus`, `make_arbitrage_data`, `make_arbitrage_data_events` и вызовы из них). Либо оформить «вход по полному кадру» в отдельной функции в `modbus_rtu_hw.c` (DMA), которая повторяет логику веток `fast_mb_begin_scan`/`next_scan`/`poll_events` из `UART_RxCplt`, но без байтового приёма. |
| Платформенный аргумент в DMA | `modbus_rtu_hw.c` (`MB_Init`) | В режиме DMA создавать и заполнять `nmbs_arg_t` (или аналог): таймер (htim), UART (huart), `TIM_Start`/`TIM_Stop`/`TIM_ReInit`, `UART_AbortReceive`. Для «отправки» в DMA использовать уже имеющийся `MB_SendFrame` (через общий callback записи в transport). Установить `nmbs->platform.arg` на эту структуру, чтобы `Timer_FastModbus` и ответы быстрого Modbus могли вызывать таймер и AbortReceive. |
| Отправка из быстрого Modbus в DMA | `fast_mb.c` или порт | В местах, где сейчас вызывается `write_serial()`, в режиме DMA вызывать отправку через текущий transport (тот же, что для обычного Modbus). Проще всего: в DMA путь использовать `platform_conf.write` (уже `MB_SendFrame`) вместо `write_serial` — т.е. ввести обёртку/макрос «send frame» или вызывать запись по `nmbs->platform` так, чтобы в DMA подставлялся `MB_SendFrame`. |
| Перезапуск приёма после быстрого Modbus | `fast_mb.c` и порт | Вместо прямых вызовов `nano_RecieveMode(nmbs)` и `fastmodbus_RecieveMode(nmbs)` ввести одну точку перезапуска приёма, например `modbus_rtu_restart_receive(&nmbs)` в `modbus_rtu_hw.c`: в IRQ она вызывает `nano_RecieveMode` / `fastmodbus_RecieveMode`, в DMA — `MB_RecieveFrame()`. В `fast_mb.c` и при необходимости в `fast_mp_port.c` заменить вызовы на эту функцию. |
| Обработка TIM14 в DMA | `stm32f0xx_it.c`, `main.c` / таймеры | Убедиться, что при `MODBUS_MODE_DMA` таймер TIM14 инициализируется (при первом кадре 0xFD) и что `HAL_TIM_PeriodElapsedCallback` для этого таймера вызывает `Timer_FastModbus(&nmbs)` так же, как в IRQ. Сейчас вызов обёрнут в `#if MODBUS_MODE_IRQ` — добавить ветку для DMA. |
| Инициализация таймера при первом 0xFD в DMA | `modbus_rtu_hw.c` или `tim.c` | При входе в быстрый Modbus по кадру 0xFD вызвать `MX_TIM_FastMB_Init(mode, &nmbs)` с нужным режимом (1/2/3/4 по протоколу), затем `HAL_TIM_Base_Start_IT(&TimerFastMB)`. Коэффициенты таймера задаёт `compute_timer()` — он должен быть доступен и при DMA (сейчас в `fast_mp_port.c` под IRQ; при необходимости вынести в общий модуль или дублировать вызов при инициализации TIM14 для DMA). |

### 3. Зависимости и порядок

- В DMA при старте приложения TIM14 для быстрого Modbus можно не запускать; запускать его при первом принятом кадре 0xFD после разбора и входа в автомат.
- `compute_timer()` должен быть вызван до первого `MX_TIM_FastMB_Init` (как в IRQ при `fast_mb_init`/`nano_RecieveMode`), иначе период таймера будет неверный.
- После завершения цикла быстрого Modbus (арбитраж + ответ) в `Timer_FastModbus` вызывается перезапуск приёма; в DMA это должно стать `MB_RecieveFrame()`, чтобы снова принимать по IDLE/RTO.

### 4. Риски и упрощения

- **Объём изменений:** затронуты `modbus_rtu_hw.c`, `fast_mb.c`, возможно `fast_mp_port.c`, `stm32f0xx_it.c`, инициализация таймера. Часть кода в `fast_mb.c` сейчас целиком под `#if MODBUS_MODE_IRQ` — потребуется аккуратно вынести общую логику (разбор, арбитраж, ответы) и добавить ветки по режиму только там, где отличается приём/перезапуск приёма/отправка.
- **Упрощение:** можно сначала реализовать только подкоманду **0x05 (poll_events)** в DMA: один ответ по событиям без многооконного арбитража. Тогда не обязательно поднимать полный цикл begin/next scan; достаточно по кадру 0xFD 0x46/0x60 0x05 вызвать проверку CRC, сформировать ответ событий и отправить его через `MB_SendFrame`, затем `MB_RecieveFrame()`. Полная поддержка 0x01/0x02 (scan) потребует уже таймера и того же `Timer_FastModbus`, что и в IRQ.

---

## Краткий вывод

Реализовать быстрый Modbus (0x46/0x60) в режиме DMA можно: вход в автомат делается один раз по полному кадру в `HAL_UARTEx_RxEventCallback`, дальнейшая работа — тот же таймер TIM14 и те же функции ответа, что и в IRQ, с подменой только перезапуска приёма (`MB_RecieveFrame`) и отправки (`MB_SendFrame`). Нужны: общая точка перезапуска приёма, платформенный аргумент и инициализация TIM14 для DMA, вызов `Timer_FastModbus` при DMA и возможность вызывать разбор 0xFD и формирование ответа из пути DMA.
