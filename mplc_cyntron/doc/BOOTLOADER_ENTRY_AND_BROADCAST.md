# Переход в режим бутлоадера и защита от broadcast

Более общий разбор причин зависаний и ошибок (ISR, critical_stop, DMA, clear_tim_flag) — см. **doc/HANG_AND_ERROR_CAUSES_ANALYSIS.md**.

## Как устройство переходит в бутлоадер

1. **Регистр 129 (holding)**  
   Запись **ненулевого** значения (Modbus 0x06 Write Single Register): приложение записывает в RAM по адресу `0x200000C0` значение `MAGIC_REBOOT_NUMBER` (0x78215348) и вызывает `HAL_NVIC_SystemReset()`. После сброса бутлоадер видит magic и **не** переходит в приложение, остаётся в режиме прошивки (красный LED мигает ~200 ms).

2. **Запись info-блока 0x1000 (16 регистров)**  
   Modbus 0x10 (Write Multiple Registers) с **адресом 4096 (0x1000)** и количеством **≥ 16**: то же действие — запись magic в RAM и сброс. Так прошивальщик переводит устройство в бутлоадер без отдельной команды по рег. 129.

Константы: `Core/Inc/main.h` (MAGIC_REBOOT_NUMBER, VECTOR_TABLE_SIZE), `bootloader/Core/Inc/bootloader_config.h` (BL_MAGIC_ADDR, BL_MAGIC_VALUE).

## Почему «зависший» мастер мог переводить все устройства в бутлоадер

Кадры Modbus с **broadcast-адресом 255 (0xFF)** обрабатываются **всеми** устройствами на линии: каждый считает запрос «для себя» и выполняет его (ответ откладывается по арбитражу, но команда записи выполняется). Адрес 255 выбран вместо стандартного 0, чтобы искажённый первый байт (0x00) не вызывал ложных срабатываний.

Если мастер (или другой хост) отправил на **broadcast (addr 255)**:
- запись в регистр 129 = 1, или  
- Write Multiple Registers по адресу 0x1000 (≥16 регистров),  

то **все** устройства выполнили бы переход в бутлоадер (magic + reset). После сброса они остаются в бутлоадере → красный LED мигает на всех. Сценарий: «мастер завис» — например, прошивальщик/скрипт перед зависанием отправил такую команду на адрес 255 (broadcast), либо один раз отправленный broadcast-кадр привёл к массовому переходу.

## Внесённая защита

Переход в бутлоадер по командам **рег. 129** и **0x10 по адресу 0x1000** **не выполняется**, если запрос пришёл по **broadcast** (адрес в кадре = 255, `NMBS_BROADCAST_ADDRESS`). В этом случае запись обрабатывается как обычно (без magic и сброса).

- Для перевода **конкретного** устройства в бутлоадер мастер должен обращаться по **его** Modbus-адресу (1…247).
- Область применения: основное приложение (Debug/Release); бутлоадер не менялся.

Реализация: в `Core/modbus/src/modbus_rtu_hw.c` перед вызовом `nmbs_server_poll` сохраняется адрес запроса (`buf[0]`); в обработчиках записи рег. 129 и 0x10 (0x1000) при `s_last_request_addr == NMBS_BROADCAST_ADDRESS` (255) переход в бутлоадер не выполняется. В пути IRQ (fast_mb.c) перед poll вызывается `modbus_rtu_set_request_addr(nmbs->msg.buf[0])`. Константа `NMBS_BROADCAST_ADDRESS = 0xFF` задана в Core/modbus/inc/modbus.h.

## Красный LED

- **В бутлоадере:** красный LED (PA11, LED1_SYS_AL) мигает с периодом 200 ms (`BL_LED_BLINK_MS` в bootloader_config.h).
- **В приложении:** красный мигает при ошибке модуля (`get_error_module() != mp02_OK`) или в режиме индикации адреса Modbus.

Если на линии все устройства синхронно мигают красным с коротким периодом (~200 ms), это типично для режима бутлоадера.

### Красный при отсутствии обмена по Modbus (>20 с)

Если мастер не опрашивает устройство более **20 секунд** (`MODBUS_IDLE_TIME` в light_indicator.c), устройство переходит в режим **индикации адреса Modbus** (MODE_LIGHT_MODBUSADDR): красный даёт короткие вспышки в цикле показа адреса. Это **нормальное** поведение, не ошибка.

В логе при включённой отладке должно появляться сообщение `[RED_LED] MODBUSADDR indication RED_ON (inactivity>20s)`. Если в логе виден только поток `[12AI] ch...`, сообщения `[RED_LED]` могут врезаться в середину строк из‑за одновременного вывода (таймер индикации и опрос AI). Сообщения `[RED_LED]` теперь начинаются с `\n`, чтобы реже сливаться с другими строками. Для удобного поиска в логе: `grep RED_LED` или временно отключить `AI_DEBUG` в main.h, чтобы уменьшить поток [12AI].

## Детальные логи перехода в режим прошивки и broadcast (COM_PORT_DEBUG)

В основном приложении при включённом COM_PORT_DEBUG выводятся сообщения с префиксом **[BOOTLOADER]** и **[Modbus]**:

| Сообщение | Значение |
|-----------|----------|
| `[Modbus] broadcast (addr 255) received...` | Принят кадр с broadcast-адресом 255. |
| `[BOOTLOADER] broadcast FC=0x06 WriteSingleReg reg=129 value=1 (reg129=bootloader)` | Broadcast: запись в регистр 129 (перевод в бутлоадер) — по такой команде все устройства ушли бы в бутлоадер без защиты. |
| `[BOOTLOADER] broadcast FC=0x10 WriteMultiReg start=4096 qty=16 (0x1000+16=bootloader)` | Broadcast: запись блока 0x1000, 16 регистров (info-блок прошивки). |
| `[BOOTLOADER] reg129 value=... broadcast IGNORED (no reset, red LED unchanged)` | Запись в рег. 129 пришла по broadcast — переход в бутлоадер не выполняется. |
| `[BOOTLOADER] reg129 value=... req_addr=... -> magic+reset (red LED in bootloader)` | Запись в рег. 129 по конкретному адресу — выполнен переход в бутлоадер (magic + сброс). |
| `[BOOTLOADER] 0x10 addr=0x1000 qty=... broadcast IGNORED (no reset...)` | Запись 0x1000 по broadcast — переход не выполняется. |
| `[BOOTLOADER] 0x10 addr=0x1000 qty=... req_addr=... -> magic+reset (red LED in bootloader)` | Запись 0x1000 по конкретному адресу — переход в бутлоадер. |

В бутлоадере при **BL_DEBUG** (PB6 115200 8N1): при входе в режим прошивки по magic выводится строка вида  
`BOOT: stay in firmware mode (app wrote magic via reg129 or 0x10 0x1000), red LED blink`.

## Ошибка «broadcast → Error_Handler» (режим IRQ)

После приёма broadcast в логе появлялось `[Modbus] broadcast (addr 255) received...`, затем `[RED_LED] Error_Handler entered - HAL error...`. Причина: вызов **nano_RecieveMode()** из контекста **прерывания** (ISR). В режиме IRQ есть два пути, где при broadcast вызывается **nano_RecieveMode()**:

1. **rtu_broadcast_tick()** — вызывается из прерывания TIM6 (10 мс), обрабатывает отложенный ответ на broadcast.
2. **Timer_FastModbus()** — вызывается из прерывания таймера Modbus (TimerFastMB); при приёме кадра с адресом 255 сразу вызывается **rtu_broadcast_schedule()** и **nano_RecieveMode()**.

В **nano_RecieveMode()** при установленном **reload_rs485** выполняются **HAL_UART_DeInit**, **ModbusUart_Init()**, **fast_mb_init()**, **MX_TIM_FastMB_Init()** — реинициализация UART/таймера **из ISR** недопустима и приводит к HAL error и Error_Handler.

**Исправление:** перед вызовом **nano_RecieveMode()** из **обоих** мест выставляется флаг «пропустить reload» (`fast_mp_port_set_skip_reload(1)`); после вызова — сброс (`fast_mp_port_set_skip_reload(0)`). В **nano_RecieveMode** блок с **reload_rs485** не выполняется, если установлен этот флаг; выполняется только перезапуск приёма. Полная реинициализация по **reload_rs485** произойдёт при следующем входе в **nano_RecieveMode** из обычного пути (не из прерывания). Режим DMA не затронут.

## Почему бутлоадер не перешёл в приложение через 2 минуты (зависание в мигании красным)

Таймаут **120 с** без активности и переход в приложение (`bootloader_jump_to_app`) в бутлоадере были реализованы **только для режима прошивки**: флаг `in_firmware_update_mode` устанавливается в **true** только после приёма **info-блока** (0x10 по адресу 0x1000) от прошивальщика. Условие перехода по таймауту было: `in_firmware_update_mode && (HAL_GetTick() - last_activity_tick) >= BL_IDLE_TIMEOUT_MS && bootloader_app_valid()`.

При входе в бутлоадер **по magic** (рег. 129 или 0x10 0x1000 из приложения) прошивальщик к устройству не подключается — info-блок в бутлоадере не приходит, `in_firmware_update_mode` остаётся **false**. В результате проверка таймаута 120 с **никогда не срабатывала**, и устройство оставалось в бутлоадере бесконечно (мигание красным).

**Исправление:** в бутлоадере введён флаг **s_entered_by_magic** (устанавливается при `user_requested_bootloader == true` при старте). Условие перехода по таймауту 120 с расширено: `(in_firmware_update_mode || s_entered_by_magic) && ...`. Таким образом, если устройство вошло в бутлоадер по magic и в течение 120 с не было активности по Modbus (ни info, ни блоки прошивки, ни опрос), бутлоадер переходит в приложение (если оно валидно). При приёме info-блока `s_entered_by_magic` сбрасывается, дальнейший таймаут учитывается только через `in_firmware_update_mode`. Область применения: конфигурация **AppBoot** (бутлоадер).
