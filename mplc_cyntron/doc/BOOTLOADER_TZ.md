# Техническое задание: бутлоадер MP-02m (протокол обновления по Modbus)

**Версия:** 1.0  
**Дата:** 2025-02-08  
**Цель:** реализация бутлоадера для проекта MP-02m, совместимого с протоколом обновления по Modbus (регистры 0x1000, 0x2000) и утилитами прошивки того же формата, без изменения существующей логики перехода в бутлоадер в приложении.

---

## 1. Область применения и ссылки

- **Проект:** MP-02m (STM32F030xC/CC, RS-485, Modbus RTU).
- **Контекст:** см. `doc/BOOTLOADER_STM32_MODBUS_ANALYSIS.md` (анализ stm32_modbus_bootloader-1.0.4, сравнение с OpenBLT, рекомендации).
- **Эталон протокола:** открытые реализации с регистрами 0x1000 (info), 0x2000 (data), формат .fw.
- **Известные ошибки (учитывать при реализации):** Bootloader Errata (см. открытую документацию по протоколу).
- **История изменений протокола:** Changelog эталонной реализации.
- **Правила проекта:** `.cursor/rules/` (safety_critical, senior_rules, workflow_and_verification).

---

## 2. Цели и ограничения

### 2.1 Цели

- Реализовать отдельный проект прошивки **бутлоадера**, размещаемый в начале или в конце Flash, который:
  - определяет запрос на вход в режим обновления по **magic в RAM** (как уже делает приложение MP-02m);
  - в режиме обновления принимает прошивку по **протоколу обновления по Modbus** (регистры 0x1000, 0x2000);
  - проверяет **сигнатуру устройства** (из EEPROM и info-блока);
  - записывает образ приложения во Flash с адреса **0x0800800**;
  - по таймауту 120 с или после успешной прошивки **запускает приложение** (VT в RAM, ремап, переход на Reset_Handler).
- Обеспечить совместимость с утилитами прошивки того же протокола (прошивка файлом .fw: переход в бутлоадер, затем отправка info 0x1000 и блоков данных 0x2000).
- Оставить без изменений поведение приложения MP-02m: запись в holding-регистр **129**, запись **MAGIC_REBOOT_NUMBER** в RAM, вызов сброса.

### 2.2 Ограничения

- **Целевой MCU:** STM32F030xC (256 КБ Flash, 32 КБ RAM); при необходимости поддержать STM32F030x8 (64 КБ Flash, 8 КБ RAM) через конфигурацию.
- **Память:** без malloc/new; статическое распределение, таймауты во всех циклах ожидания, проверки указателей и границ (см. safety_critical, senior_rules).
- **Лицензия:** код бутлоадера — тот же, что у проекта (на усмотрение заказчика).

## 3. Контекст приложения MP-02m (не менять)

- **Переход в бутлоадер:** при записи ненулевого значения в **holding-регистр 129** (0x81) приложение выполняет:
  - запись в `ram_vector[VECTOR_TABLE_SIZE]` значения **MAGIC_REBOOT_NUMBER** = `0x78215348`;
  - вызов `HAL_NVIC_SystemReset()`.
- **Размещение приложения под бутлоадер:** линкер `STM32F030CCXX_FLASH_boot.ld`: FLASH ORIGIN = **0x0800800**, LENGTH = 238 КБ; секция **.ram_vector** в RAM; макрос **BOOTLOADED**; копирование таблицы векторов из `FLASH_APP_START_ADDR` (0x0800800) в RAM и `LL_SYSCFG_SetRemapMemory(LL_SYSCFG_REMAP_SRAM)` в `main()`.
- **Константы** (из `Core/Inc/main.h`): `VECTOR_TABLE_SIZE` = (31+1+7+9) = 48; таблица векторов — 48 слов (192 байта); следующее слово — ячейка для magic. Секция `.ram_vector` в линкере приложения размещается в начале RAM; значит, адрес ячейки magic в RAM: **0x20000000 + 48*4 = 0x200000C0** (фиксированный адрес для проверки в бутлоадере).

## 4. Раскладка памяти

### 4.1 Flash (STM32F030xC, 256 КБ)

- **0x08000000 … 0x080007FF** (2 КБ) — область бутлоадера: таблица векторов и код бутлоадера (минимальный размер кода уместить в 2 КБ) **или** только таблица векторов/заглушка, а код бутлоадера — в конце Flash (на усмотрение реализации; см. п. 6).
- **0x0800800 … конец образа приложения** — приложение (сборка с `STM32F030CCXX_FLASH_boot.ld`). Стартовый адрес приложения: **FLASH_APP_START = 0x0800800**.
- **Резерв в конце Flash** (например `.network_backup` в текущем линкере приложения) — не затрагивать при записи прошивки; границу записи ограничить размером образа из info-блока.

Для варианта «бутлоадер в конце Flash» (по аналогии с stm32_modbus_bootloader): код бутлоадера в последних 16–32 КБ Flash, в первых 2 КБ — только векторы и, при необходимости, таблица/заглушка для запуска бутлоадера. Тогда приложение по-прежнему с ORIGIN 0x0800800.

### 4.2 RAM

- **0x200000C0** — фиксированный адрес проверки magic: по этому адресу после сброса бутлоадер читает 4 байта; если значение равно **0x78215348**, считать, что запрошен вход в режим обновления (120 с).
- Остальная RAM — под стек, .data/.bss бутлоадера; не использовать область 0x20000000 … 0x200000C3 под свои переменные, чтобы не затереть magic до проверки.

## 5. Протокол обновления по Modbus

### 5.1 Параметры связи в режиме бутлоадера

- Текущая реализация: **115200 8N1**. Адрес Modbus в режиме бутлоадера всегда **247** (не читается из EEPROM).
- При приёме по Modbus учитывать **проверку чётности** принятых данных, если включена чётность.
- Опционально (расширение): поддержка перехода по регистру **131** с сохранением текущей скорости и **чётности**. При реализации обязательно:
  - корректно настраивать чётность приёмопередатчика UART (ODD/EVEN), иначе при переходе по регистру 131 бутлоадер не отвечает;
  - сохранять пользовательские параметры связи до явного перехода на дефолт (регистр 129 или сброс по питанию), а не сбрасывать их после первой принятой прошивки.

### 5.2 Регистры Modbus (holding)

- **0x1000 (4096), 16 регистров (32 байта)** — **info-блок** (команда BEGIN). Запись: Modbus Write Multiple Registers (0x10). Содержимое: сигнатура устройства (12 байт, ASCII), размер прошивки в байтах (4 байта, little-endian), остальное — резерв/выравнивание до 32 байт. Формат совместим с .fw (INFO_BLOCK_SIZE 32, адрес 0x1000).
- **0x2000 (8192)** — **блок данных** (команда DATA). Запись: Modbus Write Multiple Registers (0x10). **Приложение:** 68 регистров (136 байт), запись с **0x0800800** блоками по 136 байт. **Образ бутлоадера:** 128 регистров (256 байт), 136 блоков, staging 0x0802F800–0x08038000. Порядок байт в регистрах: big-endian.
- **290, 12 регистров** — только чтение (0x03): **сигнатура устройства** (12 символов, по одному байту в регистре). Источник: EEPROM (см. п. 5.4).
- **330, 8 регистров** — только чтение (0x03): **версия бутлоадера** (строка до 8 символов, например "1.0.0").

Дополнительно (по желанию):
- **1000** — запись ненулевого: сброс настроек UART и Modbus-адреса в заводские (247, 115200 8N1 в бутлоадере).
- **1001** — запись ненулевого: сброс калибровок/настроек в EEPROM (осторожно).
- **1002** — запись ненулевого: сброс настроек устройства к умолчанию (если приложение поддерживает).
- **1003** — только чтение: максимальный размер прошивки (в блоках или байтах); для MP-02m можно вернуть константу «максимум области приложения».
- **1004** — запись ненулевого: **мгновенный переход в прошивку** без ожидания 120 с; полезно для хоста после прошивки или для выхода из режима бутлоадера по команде.

### 5.3 Последовательность прошивки

1. Хост переводит устройство в бутлоадер (через приложение: запись 1 в регистр 129 → сброс; в бутлоадере при старте проверяется magic по адресу 0x200000C0).
2. В течение 120 с бутлоадер принимает:
   - один раз **BEGIN**: запись 16 регистров по адресу 0x1000 (32 байта info: сигнатура + размер прошивки);
   - затем последовательно **DATA**: запись 68 регистров по адресу 0x2000 (136 байт) для каждого блока до полного размера из info-блока.
3. После приёма info-блока: проверка сигнатуры (см. п. 5.4); при совпадении — **полное** стирание всех страниц Flash, в которые попадёт новый образ (см. п. 8), затем запись блоков. При несовпадении сигнатуры — ответ Modbus Slave Failure (или аналог) и отказ в прошивке.
4. **Передача управления приложению только при условии:** принят полный объём данных (число байт равно размеру из info-блока); запись во Flash завершена без ошибок. Запрещается считать прошивку успешной и передавать управление, если записано меньше блоков, чем требуется (errata: при большей новой прошивке конец должен дописываться, иначе устройство перестаёт работать).
5. По завершении записи — перезапуск и запуск приложения (см. п. 7).

### 5.4 Сигнатура устройства

- **Хранение:** в EEPROM (EE24/CAT24C02, I2C). Выделить 12 байт под сигнатуру (например, фиксированный offset в пределах 256 байт; не конфликтовать с существующей разметкой `tConfig` — см. `doc/EEPROM_CAT24C02_LAYOUT.md`). Вариант: использовать свободную область EEPROM или зарезервировать диапазон (например, адреса 240..251) под сигнатуру MP-02m.
- **Содержимое:** строка ASCII, до 12 символов (например `mp02m` или `mp02m_v1`). При первой прошивке (пустая/заводская EEPROM) — принять любую сигнатуру из info-блока и записать её в EEPROM (режим «первая запись»).
- **Проверка:** при приёме info-блока сравнить сигнатуру из блока с сигнатурой из EEPROM; при несовпадении (и не «первая запись») — отказ.

## 6. Размещение кода бутлоадера

Допустимы два варианта (выбор за реализацией).

**Вариант A — бутлоадер в начале Flash (2 КБ):**  
- 0x08000000 — таблица векторов и весь код бутлоадера. Ограничение: размер образа бутлоадера ≤ 2 КБ (жёстко). Подходит при минимальном коде (только Modbus, Flash, запуск приложения).

**Вариант B — бутлоадер в конце Flash:**  
- 0x08000000 — только таблица векторов (и, при необходимости, короткая заглушка, переходящая на код в конце).  
- Код бутлоадера — в последних 16–32 КБ Flash (например 0x08038000 … 0x08040000). Тогда при старте МК выполнение начинается с 0x08000000; в векторе Reset — переход на код в конце Flash. Приложение без изменений: ORIGIN 0x0800800.

В ТЗ зафиксировать выбранный вариант и полную карту Flash в итоговой документации.

## 7. Запуск приложения из бутлоадера

После таймаута 120 с без прошивки или после успешной записи образа:

1. Отключить периферию, используемую бутлоадером (UART, таймеры и т.д.), по возможности деинициализировать.
2. Заблокировать Flash (FLASH->CR |= FLASH_CR_LOCK).
3. Проверить, что по адресу **0x0800800** лежит валидный вектор сброса (например, первое слово в диапазоне 0x0800xxxx). При невалидности (все 0xFF или мусор) — не переходить, остаться в бутлоадере или повторить попытку по таймауту.
4. Скопировать таблицу векторов приложения из **0x0800800** в RAM (в массив или секцию, размещённую по тому же адресу, что и у приложения, либо в фиксированный блок RAM с последующим ремапом).
5. Вызвать `LL_SYSCFG_SetRemapMemory(LL_SYSCFG_REMAP_SRAM)` (векторы из RAM).
6. Установить MSP: `__set_MSP(*(volatile uint32_t *)0x0800800)`.
7. Перейти на Reset_Handler приложения: `((void (*)(void))(*((uint32_t *)0x0800804)))();` (второе слово в таблице векторов — адрес Reset_Handler).

Использовать тот же порядок и те же константы, что в текущем приложении при `#ifdef BOOTLOADED` (копирование VT, ремап, переход).

## 8. Работа с Flash

- **Стирание:** стирать **все страницы**, целиком попадающие в диапазон **[0x0800800, 0x0800800 + размер_из_info_блока]** (размер выровнять вверх до границы страницы). Для STM32F030xC размер страницы 2 КБ (FLASH_PAGE_SIZE 0x800). Не оставлять непрошитыми страницы внутри этого диапазона — иначе при прошивке большего образа конец не запишется, но бутлоадер может ошибочно передать управление.
- **Запись:** полусловами (16 бит), разблокировка/блокировка по правилам HAL/LL; таймаут в циклах ожидания готовности; проверка ошибок записи (FLASH_SR). Перед передачей управления приложению убедиться, что записано ровно столько байт, сколько указано в info-блоке.
- **Защита и границы:** не писать в область бутлоадера и в служебные секции (например network_backup в конце Flash). Верхнюю границу записи ограничить `min(размер из info-блока, допустимый конец области приложения)`. Все адреса стирания и записи проверять на попадание в допустимый диапазон; не выходить за границы Flash.

## 9. Индикация (опционально)

- В режиме ожидания прошивки (120 с): редкое мигание LED (например период 1 с).
- Во время приёма блоков: изменение режима мигания или постоянное свечение до завершения.
- При ошибке (неверная сигнатура, ошибка Flash): отличный режим (например частое мигание или несколько коротких вспышек).

Использовать существующие пины/драйверы LED проекта, если бутлоадер использует ту же плату.

**RS-485:** до первого ответа по Modbus держать вывод TX (или DE/RE) в безопасном состоянии (низкий уровень), чтобы не запитывать трансивер паразитно при отключённом питании.

## 10. Формат .fw и утилита прошивки

- **Требование:** образ, принимаемый бутлоадером: сначала 32 байта info (16 регистров 0x1000), затем блоки по 136 байт (68 регистров 0x2000). В .fw данные хранятся как 16-битные слова в **big-endian**.
- **Задача:** реализовать скрипт или утилиту (Python/C), которая из **.bin приложения** (собранного с 0x0800800) формирует файл **.fw**:
  - первые 32 байта: сигнатура устройства (12 байт, ASCII, дополненная нулями), размер прошивки в байтах (4 байта, little-endian), остальное — нули/резерв;
  - далее содержимое .bin приложения, разбитое на блоки по 136 байт; каждый блок в формате 68 регистров (big-endian слова) для Modbus 0x10.
- Документировать формат .fw для MP-02m и пример вызова утилиты прошивки.

## 11. Критерии приёмки

1. После записи 1 в регистр 129 приложением устройство перезагружается и в течение 120 с отвечает на Modbus в режиме бутлоадера (9600 8N2); по чтению регистров 290 и 330 возвращаются сигнатура и версия бутлоадера.
2. После отправки info-блока (0x1000) и блоков данных (0x2000) с помощью утилиты прошивки и файла .fw, сформированного по п. 10, прошивка записывается во Flash с 0x0800800; после завершения устройство перезапускается и запускает приложение.
3. При несовпадении сигнатуры в info-блоке с сигнатурой в EEPROM прошивка не выполняется (ответ ошибки).
4. По истечении 120 с без начала прошивки или без активности бутлоадер запускает приложение, если по адресу 0x0800800 записан валидный образ.
5. Если по 0x0800800 нет валидной прошивки (например, после сбоя), бутлоадер остаётся в режиме приёма дольше 120 с (постоянно или до следующего сброса) — поведение зафиксировать в документации.
6. Соблюдены правила проекта: проверки указателей и границ, таймауты в циклах, без динамической памяти, документирование публичного API.
7. Прошивка большего по размеру образа записывается полностью; управление приложению передаётся только после приёма и записи полного числа байт из info-блока.

## 12. Учёт известных ошибок (Errata)

При реализации учитывать типичные ошибки бутлоадеров:

| Код | Суть | Мера в нашем бутлоадере |
|-----|------|--------------------------|
| **ERRBOOT001** | Чётность ODD/EVEN не работает при переходе по регистру 131 | При поддержке регистра 131 — корректная настройка чётности UART. |
| **ERRBOOT002** | После входа по 131 параметры сбрасывались после первой прошивки | При поддержке 131 — не менять параметры связи до перехода по 129 или сброса по питанию. |
| **ERRBOOT003** | Новая прошивка больше старой — конец не дописывался, управление передавалось | Полное стирание страниц под новый размер; передача управления только при полном приёме и записи (п. 5.3, 8). |
| **ERRBOOT004** | Чтение файловой системы с двойной ECC-ошибкой останавливало бутлоадер | У нас нет файловой системы в бутлоадере; при чтении EEPROM/других хранилищ — таймауты и проверки, не зависать на сбойных данных. |
| **ERRBOOT005** | Сразу переход в прошивку из-за задержки супервизора питания | Если появится проверка «power good» — учитывать задержку (например до 600 мс) перед принятием решения. |
| **ERRBOOT006** | Разрядка батареи при отключении V+: TX питал трансивер | До первого ответа по Modbus держать TX/DE в безопасном состоянии (п. 9). |
| **ERRBOOT007** | Выход за границы Flash при полной последней странице «файловой системы» | Жёсткая проверка границ при стирании/записи; не читать структуры за пределами области приложения (п. 8). |

У нас нет FlashFS в бутлоадере — требования к регистрам 1002/1003 упрощаются (при необходимости только 1004 и базовые 1000/1001).

## 13. Структура поставки и документация

- **Исходный код бутлоадера:** отдельная папка/проект (например `bootloader/` или в составе репозитория с отдельным линкером и конфигурацией сборки).
- **Документ:** краткое описание раскладки Flash/RAM, выбранного варианта размещения (A или B), адресов регистров и формата .fw; инструкция по сборке бутлоадера и приложения, формированию .fw и прошивке.
- **Скрипт/утилита:** генерация .fw из .bin приложения и заданной сигнатуры (см. п. 10).

- Линкер приложения под бутлоадер: `STM32F030CCXX_FLASH_boot.ld`.
- EEPROM: `Core/storage/`, `doc/EEPROM_CAT24C02_LAYOUT.md`; учесть разметку при добавлении хранения сигнатуры.

## 15. Устранение неполадок: сканер не находит адрес 247

Если бутлоадер по логу принимает запрос (BL rx: F7 03 …) и отправляет ответ (BL tx: F7 03 …), но мастер/сканер адрес 247 не находит:

1. **Задержка перед ответом** — в `bootloader_config.h`: `BL_TX_DELAY_BEFORE_DE_MS` (по умолчанию 2). Даёт мастеру время переключить RS-485 в приём. Если сканер шлёт запросы подряд без паузы, попробовать `0`.
2. **Инверсия DE** — если на плате DE активен по низкому уровню: `BL_DE_ACTIVE_LOW 1`.
3. **Проверка с одним устройством** — оставить на шине только устройство с адресом 247. Если сканер находит 247 — причина в коллизии/тайминге при нескольких устройствах; если не находит — проверить вывод RS-485 (DE, TX, A/B) осциллографом.
4. **Двойная отправка** — уже включена (`BL_RESPOND_TWICE 1`): ответ уходит дважды с паузой 6 ms.
