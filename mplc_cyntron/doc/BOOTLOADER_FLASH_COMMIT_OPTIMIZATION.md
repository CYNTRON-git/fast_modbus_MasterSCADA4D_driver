# Оптимизация времени commit при обновлении бутлоадера

## Ограничения железа STM32F0

- **Программирование только полусловами (16 бит).** Контроллер Flash не поддерживает запись страницы/буфера целиком; каждое программирование — запись по адресу с установленным PG и ожидание сброса BSY (~20–40 мкс по RM).
- **Нельзя «сначала всё в RAM, потом одним махом во Flash»:** программирование выполняется только записью по целевому адресу Flash при установленном PG. Отдельной команды «записать буфер из RAM» нет.
- **Минимальное время на 34 КБ:** 17408 полуслов × ~40 мкс ≈ **0,7 с** только на фазу программирования (без учёта стирания).

## Что уже сделано

1. **Ожидание по BSY, а не по фиксированной задержке**  
   После каждого полуслова ждём сброса `FLASH_SR_BSY` в цикле. Время определяется контроллером Flash (~40 мкс), а не тактовой частотой CPU, поэтому нет «30 секунд» при 8 МГц.

2. **Стирание**  
   После каждого запуска стирания страницы ждём сброс BSY (опрос раз в 2 мс, таймаут 100 мс на страницу). 17 страниц × ~25 мс ≈ 0,4 с.

3. **Итого commit:** стирание ~0,4 с + программирование ~0,7 с → **порядка 1–2 с**.

## Возможные доработки (опционально)

### 1. Пакетная запись (burst) — экспериментально

В RM не всегда явно сказано, можно ли подать несколько полуслов подряд (не сбрасывая PG и не ожидая BSY между ними) и ждать BSY один раз после группы. Если контроллер принимает несколько адресов подряд:

- Вариант: писать по 2 или 4 полуслова, затем один раз ждать BSY.
- Эффект: в 2–4 раза меньше ожиданий; время программирования может снизиться до ~0,2–0,4 с.
- Риск: на части F0 возможна только одна «активная» операция; при burst нужно проверять корректность прошивки (чтение образа после commit, тест запуска).

В коде: `BL_FLASH_COMMIT_BURST` в `bootloader_config.h` (1 = без burst, 2/4 = по 2 или 4 полуслова). По умолчанию 4 (commit op=20). Приём блоков (op=18) — без burst.

### 2. Ускорение приёма блоков по Modbus (не commit)

Время прошивки образа бутлоадера — приём 136 блоков по 256 байт и запись в staging. Можно:

- Уменьшать задержки между блоками на хосте (уже 5 мс).
- На устройстве: писать в Flash сразу по приходу блока, без лишних копирований; стирание страниц по мере необходимости, без блокирующего полного стирания региона в начале.

### 3. Что не применимо на F0

- **Запись целой страницы из буфера:** в данном Flash такого режима нет.
- **DMA в Flash:** программирование инициируется только записью по адресу Flash из CPU, DMA для программирования не используется.
- **Параллельное программирование:** один контроллер Flash, один поток операций.

## Блоки 256 байт при приёме (0x2000)

- **BL_DATA_BLOCK_SIZE_BL = 256**, 128 регистров, **136 блоков** (34816 / 256).
- **Staging:** BL_STAGING_VECTORS_START 0x0802F800 (2 КБ), BL_STAGING_CODE_START 0x08030000 (32 КБ), BL_STAGING_END 0x08038000. Последний блок: addr = 0x08037F00, addr+256 = 0x08038000 — в границах.
- **Буферы:** MODBUS_BL_FRAME_MAX = 272 (кадр 0x10: 1+1+2+2+1+256+2 = 265); nmbs.msg.buf[272]; uart_bl лимит need ≤ 272; в modbus_bl_nmbs data_bl[BL_DATA_BLOCK_SIZE_BL] = 256 B на стеке (стек 2 КБ).
- **Проверки в коде:** bootloader_config.h — BL_STAGING_TOTAL_BYTES % BL_DATA_BLOCK_SIZE_BL == 0, последний блок не выходит за BL_STAGING_END; op=18 и flash_bl_write_staging_block — (addr + BL_DATA_BLOCK_SIZE_BL) > BL_STAGING_END → отказ.

## Итог

Текущая реализация уже близка к ограничению по времени для данной Flash: ~40 мкс на полуслово и ~25 мс на стирание страницы. Дальнейшее ускорение commit возможно только за счёт экспериментального burst (2/4 полуслова с одной проверкой BSY) с обязательной проверкой корректности прошивки на целевом устройстве.
