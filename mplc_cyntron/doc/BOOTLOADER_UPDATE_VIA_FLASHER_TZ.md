# ТЗ: обновление бутлоадера через прошивальщик (Modbus)

**Версия:** 1.0  
**Дата:** 2025-02-13  
**Контекст:** BOOTLOADER_TZ.md, BOOTLOADER_INTEGRATION.md, FLASHER_WINDOWS_TZ.md.

---

## 1. Назначение и область применения

- **Цель:** обеспечить обновление прошивки **бутлоадера** (обновление версии) через тот же прошивальщик по Modbus (RS-485), что и обновление приложения, без использования ST-Link.
- **Ограничение:** бутлоадер не может перезаписать сам себя «на месте» (код выполняется из 0x08038000). Поэтому новый образ бутлоадера сначала записывается в **временную область Flash (staging)**, проверяется, затем копируется на штатные адреса (0x08000000 и 0x08038000) и выполняется сброс.
- **Область применения:** конфигурация AppBoot; прошивальщик (flasher_windows / run_flasher.py); бутлоадер с расширенным протоколом (режим «обновление бутлоадера»).

## 2. Текущая раскладка Flash (STM32F030CC, 256 КБ)

| Область              | Адрес           | Размер   | Назначение |
|----------------------|-----------------|----------|------------|
| Векторы бутлоадера   | 0x08000000      | 2 КБ     | Таблица векторов (Reset → код в 0x08038000) |
| Приложение           | 0x0800800       | до 0x08038000 | Код и данные приложения (AppBoot) |
| .network_backup      | 0x08037800      | 2 КБ     | Резерв настроек (в конце области приложения) |
| Код бутлоадера       | 0x08038000      | 32 КБ    | Исполняемый код бутлоадера |

Итого: приложение занимает 0x0800800 … 0x08037FFF (222 КБ с учётом .network_backup).

## 3. Диапазон адресов под временный образ бутлоадера (staging)

Под временное хранение нового бутлоадера выделяется **непересекающаяся с работающим бутлоадером** область в конце зоны, формально отведённой под приложение. Область приложения **уменьшается**, граница записи приложения сдвигается вниз; освобождённый диапазон резервируется под staging.

### 3.1 Константы staging

| Символ / константа           | Значение       | Размер   | Назначение |
|-----------------------------|----------------|----------|------------|
| **BL_STAGING_VECTORS_START**| 0x0802F800     | 2 КБ     | Временные векторы нового бутлоадера |
| **BL_STAGING_CODE_START**   | 0x08030000     | 32 КБ    | Временный код нового бутлоадера |
| **BL_STAGING_VECTORS_SIZE** | 0x800          | 2 КБ     | Как BL_VECTORS_SIZE |
| **BL_STAGING_CODE_SIZE**    | 0x8000         | 32 КБ    | Как BL_CODE_SIZE |
| **BL_STAGING_END**          | 0x08038000     | —        | Конец staging (совпадает с BL_CODE_ORIGIN) |

- Staging векторов: **0x0802F800 … 0x0802FFFF** (2 КБ).
- Staging кода: **0x08030000 … 0x08037FFF** (32 КБ).
- **Итого staging: 34 КБ.**

### 3.2 Новая граница области приложения

- **Конец области приложения (запись/стирание):** не выше **0x0802F800** (FLASH_APP_WRITE_END для приложения остаётся логически «до бутлоадера», но физически конец приложения для линкера и протокола обновления приложения — **FLASH_APP_END = 0x0802F800**).
- **Секция .network_backup** в линкере приложения (AppBoot) переносится так, чтобы не попадать в staging. Рекомендуемый адрес: **0x0802E800 … 0x0802EFFF** (2 КБ). Тогда конец кода/данных приложения — не выше 0x0802E800.
- В бутлоадере при обновлении **приложения** верхняя граница записи — **0x0802F800** (не стирать и не писать в staging). При обновлении **бутлоадера** запись только в диапазоны staging (0x0802F800, 0x08030000).

Итоговая карта Flash с учётом staging:

| Область              | Адрес           | Размер   |
|----------------------|-----------------|----------|
| Векторы бутлоадера   | 0x08000000      | 2 КБ     |
| Приложение           | 0x0800800       | до 0x0802E800 (код/данные) |
| .network_backup      | 0x0802E800      | 2 КБ     |
| Резерв / запрет      | 0x0802F000      | 2 КБ     |
| **Staging векторов** | **0x0802F800**  | **2 КБ** |
| **Staging кода BL**  | **0x08030000**  | **32 КБ** |
| Код бутлоадера       | 0x08038000      | 32 КБ    |

## 4. Алгоритм обновления бутлоадера

### 4.1 Общая последовательность

1. **Выбор режима в прошивальщике:** пользователь выбирает «Обновить приложение» или «Обновить бутлоадер» и указывает **один файл** прошивки: для приложения — .fw; для бутлоадера — **.elf или .bin** (образ бутлоадера).
2. **Переход в бутлоадер:** как сейчас — запись 1 в holding-регистр 129 → сброс → устройство в режиме бутлоадера.
3. **Режим «обновление бутлоадера»:**
   - Прошивальщик отправляет **специальный info-блок** (отдельный адрес или тип в 0x1000), указывающий «цель = бутлоадер» и размер образа бутлоадера (2 КБ + 32 КБ = 34 КБ, либо отдельно 2 КБ и 32 КБ).
   - Бутлоадер по этому info переводится в состояние «приём образа бутлоадера» и готовит запись в **staging** (0x0802F800 и 0x08030000), а не в 0x0800800.
   - Прошивальщик шлёт блоки данных: **сначала** 2 КБ (векторы) в staging векторов, **затем** 32 КБ (код) в staging кода. Либо один поток 34 КБ с явным разбиением (первые 2 КБ — векторы, следующие 32 КБ — код).
   - После приёма всех блоков бутлоадер проверяет образ в staging (CRC32 или проверка векторов/Reset_Handler в пределах staging).
   - При успешной проверке бутлоадер выполняет **commit**: копирует данные из staging в штатные области (0x08000000 и 0x08038000), выполняя код копирования из RAM (.ramfunc), затем сброс. После сброса выполняется уже новый бутлоадер.
   - При ошибке проверки или отмене — commit не выполняется, старый бутлоадер остаётся; можно повторить приём или выйти в приложение.

### 4.2 Детали протокола (расширение)

- **Различение «приложение» / «бутлоадер»:**  
  Вариант A — отдельный регистр «тип прошивки» (например запись в регистр **0x1001** значение **0x424C** = "BL" перед или в составе info).  
  Вариант B — отдельный адрес info для бутлоадера (например **0x1100** — 16 регистров под info бутлоадера).  
  В ТЗ зафиксировать один вариант (рекомендуется **0x1001 = 0x424C** при цели «бутлоадер», иначе — приложение).

- **Info для бутлоадера (при 0x1001 = 0x424C):**  
  По адресу 0x1000 передаётся 32 байта: сигнатура 12 байт (проверка как для приложения), размер образа бутлоадера **34 304** (0x8600) байт — фиксированно, либо два поля: size_vectors = 2048, size_code = 32768. Остальное — резерв. Бутлоадер проверяет сигнатуру и размер; при совпадении переходит в состояние приёма в staging.

- **Блоки данных для бутлоадера:**  
  Тот же регистр **0x2000**, блоки по 128 байт (64 регистра), как для приложения. Порядок: первые **16 блоков** (2048 байт) пишутся в **BL_STAGING_VECTORS_START** (0x0802F800), следующие **256 блоков** (32768 байт) — в **BL_STAGING_CODE_START** (0x08030000). Либо один линейный offset 0…34К-1 с записью в соответствующий физический адрес (0x0802F800 + offset для offset < 2048, иначе 0x08030000 + (offset - 2048)).

### 4.3 Commit (копирование staging → штатные адреса)

1. Код commit должен выполняться **из RAM** (секция .ramfunc): стирание и запись Flash в области 0x08000000 и 0x08038000 при выполнении из этих же областей недопустимо.
2. Последовательность commit:
   - Отключить прерывания (или минимизировать критические секции).
   - Стереть страницы **0x08000000** (2 КБ) и **0x08038000 … 0x0803FFFF** (32 КБ).
   - Скопировать из **0x0802F800** в **0x08000000** 2 КБ (полусловами или через временный буфер в RAM).
   - Скопировать из **0x08030000** в **0x08038000** 32 КБ (постранично или блоками с проверкой готовности Flash).
   - Заблокировать Flash, выполнить сброс (NVIC_SystemReset).
3. Таймауты и проверки ошибок Flash — как в текущем flash_bl (BL_FLASH_ERASE_TIMEOUT_MS, BL_FLASH_WRITE_TIMEOUT_MS); при ошибке на этапе commit — не сбрасывать, вернуть ошибку по Modbus (если возможно) и остаться в старом бутлоадере.

### 4.4 Проверка образа в staging перед commit

- Обязательно: проверка первого слова по BL_STAGING_VECTORS_START (начальный SP в допустимом диапазоне RAM) и второго слова (адрес Reset_Handler в диапазоне 0x08038xxx).
- Рекомендуется: CRC32 всего образа (34 КБ) в staging; прошивальщик передаёт ожидаемый CRC в info-блоке или отдельным регистром; бутлоадер после приёма считает CRC по staging и сравнивает. При несовпадении — отказ commit, ответ с кодом ошибки.

## 5. Требования к прошивальщику (ПК)

- **Режим «Обновить бутлоадер»:** отдельная опция в GUI (переключатель или пункт меню «Прошивка приложения» / «Прошивка бутлоадера»).
- **Файл образа бутлоадера — один файл .elf или .bin:**
  - **.bin:** считать файл как непрерывный образ 34 КБ: байты 0–2047 — векторы (запись в staging 0x0802F800), байты 2048–34815 — код (запись в staging 0x08030000). Если файл длиннее 34 КБ — использовать первые 34 КБ; если короче — ошибка «неверный размер образа бутлоадера».
  - **.elf:** из образа бутлоадера (собранного с линкером bootloader: VECTORS 0x08000000, FLASH 0x08038000) извлечь загружаемые сегменты: данные для 0x08000000 (до 2 КБ) и для 0x08038000 (до 32 КБ). Сформировать один поток для отправки: сначала 2 КБ векторов (дополнить 0xFF до 2 КБ при необходимости), затем 32 КБ кода (дополнить 0xFF до 32 КБ). Итоговый размер потока — 34 КБ.
- **Последовательность отправки:** переход в бутлоадер (регистр 129) → пауза 2 с → запись в регистр 0x1001 значения 0x424C (режим «бутлоадер») → запись info по 0x1000 (сигнатура + размер 34 КБ) → отправка блоков по 0x2000: 16 блоков по 128 байт (векторы), затем 256 блоков по 128 байт (код). При использовании CRC — расчёт CRC32 по сформированному образу 34 КБ и передача в info или отдельным запросом.
- **Прогресс и ошибки:** отображать прогресс «Бутлоадер: блок N из M»; при ответе «ошибка» (и при необходимости чтении регистров 0xF1/0xF2) выводить сообщение пользователю.

## 6. Изменения в проекте

### 6.1 Линкер приложения (AppBoot)

- В **STM32F030CCXX_FLASH_boot.ld**: уменьшить LENGTH FLASH так, чтобы конец образа приложения был не выше **0x0802F000** (оставляя 0x0802F800…0x08037FFF под staging). Секцию **.network_backup** перенести, например, на **0x0802E800** (2 КБ), чтобы она не пересекалась со staging. Константа FLASH LENGTH = (0x0802F800 - 0x0800800) = 0x27800 = 158 КБ (приложение 156 КБ + 2 КБ backup до 0x0802F000).

### 6.2 Бутлоадер

- **bootloader_config.h:** добавить константы BL_STAGING_VECTORS_START, BL_STAGING_CODE_START, BL_STAGING_END, BL_STAGING_VECTORS_SIZE, BL_STAGING_CODE_SIZE; при наличии режима «обновление бутлоадера» — FLASH_APP_WRITE_END для режима «приложение» считать 0x0802F800 (или ввести FLASH_APP_END = 0x0802F800).
- **Протокол:** обработка регистра 0x1001 (или выбранного варианта) и info 0x1000 с типом «бутлоадер»; приём блоков в staging по описанному порядку; проверка образа; команда commit (отдельный регистр, например 0x1006 «выполнить commit бутлоадера» — запись ненулевого значения после успешной проверки).
- **Flash (flash_bl):** функции стирания/записи для диапазонов staging и для commit (стирание/запись 0x08000000 и 0x08038000 из кода в RAM). Жёсткие проверки границ: запись только в разрешённые области.

### 6.3 Скрипты и сборка

- **make_fw.py** или аналог: при сборке .fw для **приложения** использовать FLASH_APP_END = 0x0802F800. Для обновления бутлоадера прошивальщик принимает **один файл** образа бутлоадера: **.elf** (например `bootloader/build/mp-02m_bootloader.elf`) или **.bin** 34 КБ (первые 2 КБ — векторы, далее 32 КБ — код; при сборке бутлоадера можно склеить два BIN в один скриптом/целью make при необходимости).
- **merge_combined.py:** без изменений для текущего combined-образа; при сборке полного образа с новым линкером приложения учёт новой границы приложения выполняется автоматически по размерам BIN. После введения staging верхняя граница приложения в merge — 0x0802F800 (дополнительно не заполнять staging в boot_fw.bin при полной прошивке через ST-Link).

## 8. Безопасность и отказоустойчивость

- **Commit только после проверки:** CRC и/или проверка векторов в staging; при ошибке — не перезаписывать рабочий бутлоадер.
- **Таймауты:** все циклы ожидания Flash (стирание, запись) — с таймаутом; при срабатывании — отмена операции и ответ об ошибке.
- **Границы:** любая запись/стирание проверять на принадлежность допустимому диапазону (приложение до 0x0802F800, staging 0x0802F800…0x08037FFF, commit — только 0x08000000 и 0x08038000).
- **Один commit за сессию:** после успешного commit устройство сбрасывается и работает уже новый код; повторный приём в той же сессии не требуется.
