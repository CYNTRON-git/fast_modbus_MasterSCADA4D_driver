# CI/CD и унификация сборки MP-02m

Предложения по улучшению унификации основного проекта на основе [статьи Wiren Board «CI/CD для микроконтроллеров»](https://wirenboard.com/ru/contents/articles/wb_ci_cd) и практик CI/CD для embedded.

---

## 1. Резюме статьи Wiren Board

### Качество кода и процессы (до CI)
- **Git** — контроль версий.
- **Style guide** — единая структура и стиль кода.
- **Code review** — на этапе внедрения фичи/правки бага.
- **Workflow** — инструкции: как выполнять задачи, что делать в типовых ситуациях.

### Воспроизводимость сборки
- **Конфигурации** — не размазывать `#ifdef MODEL_A` по коду; вынести отличия ревизий/моделей в **общий config** (например `config.h`), логику завязать на **наличие функции**, а не на модель.
- **Сборочная машина** — сборка из `git clone` на отдельной машине/CI; один `make` может собирать все таргеты (все ревизии/устройства).
- **Не Eclipse как источник правды** — тяжёлый, версии, xml-конфиг плохо ревьюится. У WB переход на **gcc + make + ~150 строк Makefile-инклюдов** (общих для проектов).

### Версии
- **Semver** (MAJOR.MINOR.PATCH) — задаётся вручную при merge в стабильную ветку.
- В прошивке хранить: сигнатура, хеш коммита, дата сборки, ветка — для отладки и техподдержки.
- **Changelog** — человекочитаемое описание изменений при релизе (в репозитории).
- **Публичная Errata** (опционально) — известные ошибки устройства.

### Тестирование
- Ручное по чек-листам.
- Функциональное на производстве (стенды) — можно использовать и при разработке.
- **Юнит-тесты** — код, отделимый от железа (алгоритмы, преобразования), собирать под x86 с теми же заголовками/исходниками и гонять на хосте.

### Развёртывание (CD)
- Загрузчик по RS-485 (у WB — подмножество Modbus RTU), шифрование прошивок, проверка сигнатуры устройства.
- Сборка прошивок на билд-сервере; артефакты — под все сигнатуры/таргеты.
- Доставка: выкладка на хранилище (по сигнатурам и версиям), утилита обновления (у WB — `wb-mcu-fw-updater`).

## 2. Текущее состояние проекта MP-02m

| Аспект | Состояние |
|--------|-----------|
| **Сборка** | STM32CubeIDE (Eclipse) — `.cproject`. Конфигурации: Debug, Release, AppBoot. Makefile генерируется IDE в `Debug/`, `Release/`, `AppBoot/`. |
| **Бутлоадер** | Отдельный **Makefile** в `bootloader/` — можно собирать из корня: `make -C bootloader -j`. |
| **Версия** | Жёстко в `Core/Inc/main.h`: `MAJOR_VER`, `MINOR_VER`, `PATCH_VER`, `SUFFIX_VER`. Есть комментарий «@todo в будущем брать из автосборки». |
| **Единая сборка** | Нет корневого Makefile «собрать всё». `production_flasher_stlink/build_combined.py` ожидает уже собранные ELF (bootloader + AppBoot) и вызывает `bootloader_maker/build_combined_from_elf.py`. |
| **Конфигурации** | Отличия Debug/Release/AppBoot — в .cproject (линкер, макросы BOOTLOADED, STM32F030xC). Варианты плат (HARDWARE_MP 21/22) частично в коде. |
| **CI** | В корне проекта **нет** GitHub Actions / Jenkins. Есть только в субмодуле `Modules/nanoMODBUS` (cmake, тесты, примеры). |
| **Changelog / Errata** | Нет единого CHANGELOG; в `doc/` есть разрозненные .md (в т.ч. WIRENBOARD_ERRATA.md). |
| **Доставка** | `flasher_windows/`, `production_flasher_stlink/`, `run_flasher.py`. Обновление по Modbus и по ST-Link документировано в `doc/BOOTLOADER_INTEGRATION.md`. |

## 3. Варианты улучшения унификации

### 3.1 Воспроизводимая сборка (приоритет высокий)

**Цель:** одна команда из корня репозитория собирает все нужные артефакты без зависимости от IDE.

**Варианты:**

- **A) Корневой Makefile (рекомендуется)**  
  - В корне добавить `Makefile`, который:
    - Собирает бутлоадер: `$(MAKE) -C bootloader -j`.
    - Собирает приложение для Debug / Release / AppBoot через **тот же тулчейн**, что и IDE (arm-none-eabi-gcc), но с явными флагами и путями (скопированными из .cproject или вынесенными в include).
  - Плюсы: не нужен Eclipse на CI, один `make all` или `make release appboot bootloader`, артефакты в предсказуемых путях (`out/Release/`, `out/AppBoot/`, `bootloader/build/`).
  - Минусы: нужно поддерживать два источника правды (IDE и Make) или генерировать Make из .cproject (сложнее).

- **B) Генерация Make из .cproject**  
  - Скрипт (Python/CMake), который парсит .cproject и генерирует Makefile для каждой конфигурации.  
  - Плюсы: один источник правды — IDE.  
  - Минусы: хрупкость парсинга XML, обновления CubeIDE могут сломать генератор.

- **C) Постепенная миграция на CMake**  
  - Один `CMakeLists.txt` для приложения (с вариантами Debug/Release/AppBoot) и отдельный для бутлоадера.  
  - Плюсы: кроссплатформенность, привычно для CI, удобно подключать субмодули.  
  - Минусы: большой объём переноса, текущий проект на CubeIDE без CMake.

**Рекомендация:** начать с **варианта A** — один корневой Makefile с целями `bootloader`, `app`, `appboot`, `release`, и при необходимости `combined.bin`. Пути include и флаги можно вынести в `make/config.mk` (или несколько файлов по конфигурации), чтобы не дублировать длинные списки.

**Реализовано в проекте:** корневой `Makefile` и каталог `mk/` (toolchain.mk, rules.mk, version.mk, pack.mk). Цели: `make` / `make BUILD_CFG=Debug|Release|AppBoot`, `make all_targets`, `make pack`, `make -C bootloader`. См. `make help` и `mk/README.md`.

### 3.2 Единая точка версии и Semver

**Цель:** версия в одном месте, при сборке подставляется в прошивку (и при необходимости в имя артефакта).

**Варианты:**

- **A) Файл `version.txt` или `version.mk` в корне**  
  - Содержит `MAJOR=2`, `MINOR=0`, `PATCH=0`, `SUFFIX=0`.  
  - Корневой Makefile и/или скрипт сборки читают его и передают в компилятор через `-DMAJOR_VER=$(MAJOR)` и т.д.  
  - В `main.h` убрать жёсткие `#define MAJOR_VER 2` и заменить на `#ifndef MAJOR_VER` / дефолты или только `#include "version_auto.h"`, который генерируется сборкой.

- **B) Генерация заголовка при сборке**  
  - Make/CMake генерирует `Core/Inc/version_auto.h` (или `build/version_auto.h`) с `MAJOR_VER`, `MINOR_VER`, `PATCH_VER`, `SUFFIX_VER`, опционально `GIT_HASH`, `BUILD_DATE`.  
  - `main.h` подключает этот заголовок.  
  - Плюсы: одна точка правды (файл версии или CI-переменные), в бинарник попадает и хеш коммита для отладки.

**Рекомендация:** A + B: версия в `version.txt` или в переменных окружения (CI), при сборке генерируется `version_auto.h` с версией и, по возможности, `GIT_SHA`, `BUILD_DATE` — и подключается в `main.h`.

### 3.3 Конфигурация устройств и ревизий (config.h)

**Цель:** не размазывать `#ifdef HARDWARE_MP_21` по коду; иметь один конфиг «какие функции/модули есть у этой ревизии».

**Варианты:**

- **A) Один `Core/Inc/config.h` (или `config/board_mp02m.h`)**  
  - Определяет набор макросов: тип платы, наличие модулей (DO6, AO6AI6, 12AI, …), пины, тайминги.  
  - Остальной код проверяет только «есть ли функция» (например `#if defined(USE_ADS1220)`), а не номер ревизии.  
  - Для разных ревизий — разные файлы конфига или один файл с `#if BOARD_REV >= 21` и т.д.

- **B) Сохранить текущий подход**  
  - Оставить выбор платы в `main.h` (TYPE_MODULE, HARDWARE_MP) и точечные `#if` в драйверах.  
  - Улучшить только документирование: в README или в `doc/` явно перечислить, какая конфигурация для какой ревизии.

**Рекомендация:** двигаться к **A** по мере появления новых ревизий: вынести общие опции в `config.h`, в `main.h` оставить только включение этого конфига и минимальные переопределения (если нужны). Это упростит добавление новой ревизии и снизит риск забыть обновить один из разбросанных `#ifdef`.

---

### 3.4 CI (GitHub Actions или аналог)

**Цель:** на каждый push/PR собирать все конфигурации и, по возможности, проверять целостность.

**Варианты:**

- **A) GitHub Actions**  
  - Workflow: checkout, установка arm-none-eabi-gcc, сборка бутлоадера (`make -C bootloader`), сборка приложения (Debug/Release/AppBoot через корневой Makefile или см. п. 3.1).  
  - Артефакты: `mp-02m_bootloader.elf`, `mp-02m.elf` (AppBoot), при желании `combined.bin`.  
  - Опционально: шаг «собрать combined.bin» через `python production_flasher_stlink/build_combined.py` (если пути к ELF зафиксированы после сборки).

- **B) Локальный Jenkins / GitLab CI**  
  - Аналогичные шаги на своём сервере; артефакты складывать в артефакт-хранилище или на внутренний файл-сервер.

**Рекомендация:** внедрить **минимальный GitHub Actions** (вариант A): одна job «Build» — установка тулчейна, `make bootloader`, `make appboot` (и при наличии корневого Make — `make release`). Это даст воспроизводимую сборку и проверку, что после изменений всё компилируется для всех целей.

---

### 3.5 Changelog и версионирование релизов

**Цель:** понятно, что изменилось в релизе; версия по Semver при merge в стабильную ветку.

**Варианты:**

- **A) Файл CHANGELOG.md в корне**  
  - Формат в духе «Keep a Changelog»: заголовки по версиям (например `## [2.0.1] - 2025-02-11`), списки Added/Changed/Fixed.  
  - Обновляется вручную при подготовке релиза (при присвоении версии в `version.txt` или в теге).

- **B) Только теги и описание в Release (GitHub)**  
  - Версия = тег (`v2.0.1`). Описание изменений пишется в тексте Release при создании.  
  - Отдельного CHANGELOG.md можно не вести, если достаточно релизов на GitHub.

**Рекомендация:** завести **CHANGELOG.md** (вариант A) и правило: при merge в `main`/релизную ветку обновлять версию и блок в CHANGELOG. Это совместимо с подходом WB и упрощает техподдержку и сравнение версий.

---

### 3.6 Единый сценарий «прошивка для производства»

**Цель:** один повторяемый способ получить образ для серийного прошивальщика (combined.bin с серийником и т.д.) без ручного запоминания шагов.

**Текущее состояние:**  
`production_flasher_stlink/build_combined.py` ожидает уже собранные ELF; в README и `doc/BOOTLOADER_INTEGRATION.md` описаны шаги.

**Улучшения:**

- **A) Цель в корневом Makefile**  
  - Например `make production` или `make combined`:  
    1) сборка бутлоадера;  
    2) сборка AppBoot;  
    3) вызов `python production_flasher_stlink/build_combined.py` (и при необходимости передача серийника через переменную/файл).  
  - Имена и пути ELF зафиксировать в Makefile и в скрипте, чтобы они совпадали.

- **B) Скрипт-обёртка `scripts/build_production.sh` (или .py)**  
  - Выполняет те же шаги; вызывается вручную или из CI.  
  - Внутри может вызывать `make -C bootloader`, затем сборку приложения (через make или IDE-команду), затем `build_combined.py`.

**Рекомендация:** после появления корневого Makefile (п. 3.1) добавить цель `production` / `combined` (вариант A) и описать её в README и в `doc/BOOTLOADER_INTEGRATION.md`, чтобы «как собрать прошивку для производства» было одной командой и одним местом в документации.

### 3.7 Юнит-тесты на хосте (x86)

**Цель:** тестировать алгоритмы и преобразования данных (таблицы термопар, NTC, PT100, расчёт CRC и т.п.) без железа.

**Варианты:**

- **A) Отдельная директория `tests/` или `unittests/`**  
  - Исходники, которые компилируются с теми же `Core/tables/*.c` и заголовками, но под обычный gcc (x86).  
  - Один `main()` с вызовами проверок (например проверка граничных значений таблиц, известных точек).  
  - Запуск: `make -C tests` или `python -m pytest` при переходе на pytest для тестов.

- **B) Не вводить пока**  
  - Оставить только ручные и интеграционные проверки.

**Рекомендация:** по мере появления времени завести минимальный набор тестов (вариант A) для таблиц и расчётов в `Core/tables/` и других аппаратно-независимых модулей — по опыту WB это даёт хороший выигрыш при малых затратах.

## 4. План внедрения (по приоритету)

| Шаг | Действие | Область применения |
|-----|----------|--------------------|
| 1 | Ввести **корневой Makefile** с целями: `bootloader`, `appboot`, при желании `release`, `clean`. Пути и флаги — в include-файлах или в начале Makefile. | Все конфигурации (сборка без IDE). |
| 2 | Ввести **единую версию**: `version.txt` или переменные + генерация `version_auto.h` при сборке; подключить в `main.h`, убрать жёсткие `#define` версии. | Все конфигурации. |
| 3 | Добавить цель **`make production`** (combined.bin), задокументировать в README и в `doc/BOOTLOADER_INTEGRATION.md`. | Производство, CI. |
| 4 | Настроить **GitHub Actions**: сборка bootloader + AppBoot (и при наличии — Release) на push/PR. | Ветки main/develop. |
| 5 | Завести **CHANGELOG.md** и правило обновления версии при релизе (Semver). | Релизы. |
| 6 | Постепенно выносить отличия ревизий в **config.h** (унификация конфигурации устройств). | Все ревизии. |
| 7 | При необходимости добавить **юнит-тесты** для таблиц и расчётов на x86. | Качество. |
