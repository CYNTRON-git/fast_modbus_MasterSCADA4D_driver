# Внедрение бутлоадера в проект MP-02m

Пошаговая инструкция: как собрать бутлоадер и приложение под бутлоадер, как прошивать устройство в первый раз и как обновлять прошивку по Modbus.

---

## 1. Общая схема

| Образ | Назначение | Линкер | Результат |
|-------|------------|--------|-----------|
| **Бутлоадер** | Код в конце Flash, векторы в начале | `bootloader/STM32F030CCXX_bootloader.ld` | Один ELF с двумя регионами: 0x08000000 (2 КБ), 0x08038000 (32 КБ); программатор при одной загрузке пишет оба |
| **Приложение без бутлоадера** | Обычная прошивка (вся Flash с 0x08000000) | `STM32F030CCXX_FLASH.ld` | Один образ с 0x08000000 |
| **Приложение под бутлоадер** | Работает после бутлоадера, переход по регистру 129 | `STM32F030CCXX_FLASH_boot.ld` + макрос **BOOTLOADED** | Образ с 0x0800800, файл .fw для обновления по Modbus |

**Отладка бутлоадера (поиск зависания при прошивке через ST-Link):** включён макрос **BL_DEBUG** — на пине **PA4** выводятся этапы инициализации короткими импульсами (1 импульс = этап 1, 2 = этап 2, … 6 = вход в основной цикл). Подключите осциллограф/логический анализатор или LED к PA4 и по последнему количеству импульсов определите, где зависание (подробнее — `bootloader/README.md`). Для релиза уберите `-DBL_DEBUG` и `#define BL_DEBUG`.

Приложение **уже умеет** переходить в бутлоадер: запись 1 в holding-регистр 129 → запись magic в RAM → сброс. Нужно только собирать его с линкером «под бутлоадер» и макросом `BOOTLOADED`, когда используете обновление по Modbus.

## 2. Конфигурации сборки в STM32CubeIDE

### 2.1 Текущие конфигурации (Debug / Release)

- Линкер: **STM32F030CCXX_FLASH.ld** (приложение с 0x08000000, без бутлоадера).
- Используйте их для отладки или для прошивки «одним куском» через ST-Link.

### 2.2 Конфигурация AppBoot (приложение под бутлоадер)

Собирает **приложение под бутлоадер** (образ с 0x0800800, линкер `STM32F030CCXX_FLASH_boot.ld`, макрос **BOOTLOADED**): ELF в `AppBoot/mp-02m.elf`, прошивка по ST-Link через **mp-02m AppBoot.launch**. Для чипа с 256 КБ Flash (STM32F030CC) обязателен макрос **STM32F030xC**.

### 2.3 Новая конфигурация: приложение под бутлоадер (AppBoot)

Нужна для сборки образа, который будет обновляться по Modbus (файл .fw).

1. **Project → Build Configurations → Manage… → New:** имя `AppBoot`, скопировать из **Release** (или Debug).
2. В **AppBoot** для **всех инструментов**, где задаётся линкер:
   - **Linker Script (-T):** заменить на  
     `${workspace_loc:/${ProjName}/STM32F030CCXX_FLASH_boot.ld}`
3. В **C/C++ Build → Settings → MCU GCC Compiler → Preprocessor** (и при необходимости MCU G++ Compiler):
   - **Define symbols (-D):** добавить **BOOTLOADED**
4. Сохранить, собрать конфигурацию **AppBoot**.

В результате в папке сборки (например `AppBoot/`) появятся `mp-02m.elf` и `mp-02m.bin` — образ приложения с начала 0x0800800. Его можно превращать в .fw скриптом `make_fw.py`.

### 2.4 Образ бутлоадера (отдельно от конфигураций проекта)

Конфигурация сборки бутлоадера **удалена из проекта** mp-02m. Образ бутлоадера (векторы 0x08000000, код 0x08038000) собирается из корня проекта:
```bash
make -C bootloader -j
```
Результат: `bootloader/build/mp-02m_bootloader.elf`. Альтернатива: отдельный проект в STM32CubeIDE или `cd bootloader && make -j`.

Образ бутлоадера — один ELF с двумя секциями (LMA). **Зачем два адреса:** после сброса процессор читает векторы с **0x08000000** (там 2 КБ векторов бутлоадера), основной код — в **0x08038000** (32 КБ), середина Flash (0x0800800 … 0x08037FFF) — под приложение. При одной загрузке ELF через ST-Link оба региона заполняются автоматически.

### 2.5 Объединённая прошивка (boot_fw.bin) — как Debug/Release

Чтобы собирать прошивку с бутлоадером и приложением **стандартными средствами**, как конфигурации Debug/Release:

**В STM32CubeIDE:** выберите конфигурацию **AppBoot** (как Debug или Release) и нажмите **Build**. Собираются **mp-02m.elf** и **mp-02m.bin** в папке AppBoot. Объединённый образ **boot_fw.bin** в IDE не создаётся — так сборка не зависит от Python/make в PATH и всегда завершается успешно.

**Объединённая прошивка (boot_fw.bin)** — из корня проекта в командной строке:

- **`make boot_fw`** — принудительная сборка каждый раз: бутлоадер + **AppBoot/mp-02m.elf** (IDE) → **build/AppBoot/boot_fw.bin**. Рекомендуется после сборки в CubeIDE.
- **`make combined`** — образ из **build/AppBoot/** (сборка корневым Makefile) → **build/AppBoot/boot_fw.bin**.

Для прошивки по 0x08000000 (ST-Link, серийный прошивальщик) используйте **build/AppBoot/boot_fw.bin**.

После `make pack` файл **boot_fw.bin** копируется в **out/**, если он уже собран.

**Область применения:** конфигурация **AppBoot** (линкер `FLASH_boot.ld`, макрос `BOOTLOADED`). Конфиги Debug и Release собирают приложение без бутлоадера и не создают boot_fw.bin.

**boot_fw.bin:** в конфигурации AppBoot Post-build шаг не используется. CubeIDE по умолчанию создаёт **.elf**, а не .bin. После сборки в CubeIDE выполните из корня проекта: **`make boot_fw`** — каждый раз принудительно собирается бутлоадер, из **AppBoot/mp-02m.elf** через `objcopy -O binary` получается образ приложения, затем склейка в **build/AppBoot/boot_fw.bin**. Цель **`make combined`** использует приложение из **build/AppBoot/** (сборка корневым Makefile).

## 3. Первая прошивка (устройство без бутлоадера)

Цель: записать бутлоадер и первое приложение.

### Шаг 1: Прошить бутлоадер

1. Собрать образ бутлоадера (отдельный проект или вручную, см. п. 2.4).
2. Подключить ST-Link и **один раз** загрузить образ бутлоадера (ELF). ST-Link/CubeProgrammer по одному ELF сами запишут оба региона: векторы в 0x08000000 (2 КБ) и код в 0x08038000 (32 КБ). Два отдельных прохода по разным адресам не нужны.
3. Убедиться, что заняты:
   - 0x08000000 … 0x080007FF (векторы),
   - 0x08038000 … конец кода бутлоадера (32 КБ).

### Шаг 2: Прошить приложение

**Способ A — через ST-Link / STM32CubeProgrammer**

- Собрать конфигурацию **AppBoot**, получить .bin (например `AppBoot/mp-02m.bin`).
- В программе прошивки (STM32CubeProgrammer / OpenOCD) записать этот .bin **строго по адресу 0x0800800** (не 0x08000000). Образ приложения под бутлоадер собран для 0x0800800; при записи с 0x08000000 векторы и код окажутся не на своих местах — устройство будет зависать после сброса.
- Не стирать области 0x08000000 (векторы бутлоадера) и 0x08038000 (код бутлоадера). При использовании ELF программатор сам подставляет адреса из образа; при ручной загрузке .bin обязательно указать **Start address: 0x0800800**.

**Способ B — через Modbus (если бутлоадер уже прошит)**

- Собрать **AppBoot** → сделать .fw:  
  `python bootloader/scripts/make_fw.py -i AppBoot/mp-02m.elf -s mp02m -o mp02m.fw`
- Перевести устройство в бутлоадер: записать 1 в holding-регистр 129 (адрес Modbus 1, 9600 8N2 по умолчанию после сброса).
- В течение 120 с выполнить прошивку:  
  `flasher -j -d COM3 -a 1 -f mp02m.fw`  
  (порт и адрес — под вашу схему.)

После успешной записи устройство перезапустится и запустит приложение.

## 4. Обновление прошивки по Modbus (уже с бутлоадером)

Когда бутлоадер уже в устройстве, обновление делается без ST-Link.

1. **Собрать приложение под бутлоадер:** конфигурация **AppBoot** → `mp-02m.elf` / `mp-02m.bin`.
2. **Сформировать .fw:**  
   `python bootloader/scripts/make_fw.py -i AppBoot/mp-02m.elf -s mp02m -o mp02m_1.0.1.fw`  
   Сигнатура `-s` должна совпадать с записанной в EEPROM устройства (см. ниже).
3. **Перевести устройство в бутлоадер:** через текущее приложение записать 1 в holding-регистр **129**.
4. В течение **120 секунд** выполнить прошивку утилитой (например из `flasher_windows` или wb-mcu-fw-flasher):  
   `flasher -j -d COM3 -a 1 -f mp02m_1.0.1.fw`

После завершения устройство перезапустится и запустит новую прошивку.

---

## 5. Сигнатура устройства (EEPROM)

Бутлоадер проверяет сигнатуру из info-блока файла .fw с данными в EEPROM (байты **240..251**, см. `bootloader_config.h`: `BL_SIGNATURE_EEPROM_OFFSET`). Параметр **-s** в `make_fw.py` (например `-s mp02m`) задаёт сигнатуру в .fw; она должна совпадать с той, что в EEPROM. При первой прошивке через бутлоадер сигнатура из .fw записывается в EEPROM. Подробнее: `doc/BOOTLOADER_TZ.md`, `doc/EEPROM_CAT24C02_LAYOUT.md`.

## 6. Краткий чек-лист

| Задача | Действие |
|--------|----------|
| **Одна прошивка (бутлоадер + приложение)** | **`make boot_fw`** (принудительно, из AppBoot/mp-02m.elf) или **`make combined`** → **build/AppBoot/boot_fw.bin** (256 КБ, прошивать по 0x08000000) |
| Сборка приложения для обновления по Modbus | Конфигурация **AppBoot** (линкер `FLASH_boot.ld`, макрос `BOOTLOADED`) |
| Сборка бутлоадера | `make -C bootloader` (линкер `bootloader/STM32F030CCXX_bootloader.ld`, исходники в `bootloader/Core`) |
| Получить файл .fw | `python bootloader/scripts/make_fw.py -i <app.elf или app.bin> -s mp02m -o app.fw` |
| Переход в бутлоадер | Записать 1 в holding-регистр 129 |
| Прошивка по Modbus | В течение 120 с: `flasher -j -d COMx -a <addr> -f app.fw` |
| Первая прошивка бутлоадера | ST-Link: образ в 0x08000000 и 0x08038000 |
| **Обновление бутлоадера** | **Только через ST-Link** (по Modbus нельзя: протокол пишет только приложение 0x0800800) |

## 7. Устранение неполадок: «программа зависает», прошивальщик не может прошить

Если после записи 1 в регистр 129 устройство перезагружается, но прошивальщик не видит бутлоадер или «зависает»:

1. **В Flash нет бутлоадера**  
   После сброса выполняется снова приложение (по векторной таблице с 0x08000000). Прошивальщик ждёт ответ по протоколу бутлоадера (9600 8N2, регистры 0x1000/0x2000), а устройство отвечает как обычное приложение (другая скорость/формат).  
   **Решение:** один раз прошить бутлоадер через ST-Link (регионы 0x08000000 и 0x08038000), затем пользоваться обновлением по Modbus.

2. **На устройстве стоит приложение не из конфигурации «под бутлоадер»**  
   Если прошита сборка Debug/Release (без BOOTLOADED), переменная `ram_vector` не лежит по адресу 0x200000C0, запись magic может не сработать так, как ожидает бутлоадер. Для перехода в бутлоадер по регистру 129 на устройстве должна быть прошивка, собранная с **AppBoot**: линкер `STM32F030CCXX_FLASH_boot.ld` и макрос **BOOTLOADED**.

3. **Скорость и формат порта**  
   В режиме бутлоадера используется **115200 8N1**. Адрес Modbus всегда **247**. Проверьте в прошивальщике: порт (COMx), скорость 115200, 8N1, адрес устройства 247.

4. **Зависание бутлоадера при инициализации**  
   Если бутлоадер «висит» до первого ответа, возможна блокировка в инициализации UART или I2C/EEPROM. В коде бутлоадера при ошибке инициализации UART делается попытка перейти в приложение (если образ валиден), чтобы не зависнуть навсегда. Убедитесь, что пины RS-485 (PA1=DE, PA2=TX, PA3=RX) и при необходимости I2C EEPROM не замкнуты и соответствуют схеме.

5. **Запись в регистр 129**  
   Переход в бутлоадер делается записью **ненулевого значения** в holding-регистр **129** (одна запись 0x06 или запись в рамках 0x10). Убедитесь, что прошивальщик или тестовый скрипт действительно выполняют эту запись перед попыткой прошивки.

6. **При прошивке бутлоадера/AppBoot ELF через CubeIDE «программа сразу зависает»**  
   Образ приложения под бутлоадер занимает только область с **0x0800800**. Если перед загрузкой выполняется **полное стирание Flash**, обнуляются **0x08000000** (векторы бутлоадера) и **0x08038000** (код бутлоадера). После сброса CPU читает SP/PC с 0x08000000 → 0xFFFFFFFF → зависание.  
   **Рекомендуемый порядок:** один раз прошить бутлоадер через ST-Link (образ собран отдельным проектом или вручную). Дальше при Run/Debug с **AppBoot** загрузчик обычно стирает только сектора образа (с 0x0800800) — бутлоадер сохраняется. Если после загрузки устройство зависает (полное стирание) — после каждой такой прошивки заново прошивайте бутлоадер или используйте обновление по Modbus (.fw) после перехода в бутлоадер по регистру 129.

7. **Ошибка «Identify the modified sectors for the segment 0/1» и «Error when opening … STM32_Programmer_CLI.exe»**  
   Появляется, если в конфигурации запуска включена **Incremental flashing**: IDE пытается вызвать **STM32CubeProgrammer CLI** для инкрементальной прошивки, но не находит исполняемый файл (не установлен или другой путь в вашей версии IDE).  
   **Что сделать:** в конфигурации **AppBoot** опция **Incremental flashing** выключена (`false`), чтобы использовалась загрузка через GDB/ST-Link без вызова CubeProgrammer. Если включили Incremental flashing — отключите: **Run → Debug Configurations… → вкладка Startup** — снимите **Incremental flashing**.  
   Либо установите **STM32CubeProgrammer** и при необходимости укажите в IDE правильный путь к `STM32_Programmer_CLI.exe`.

8. **AppBoot при прошивке через STM32CubeProgrammer «по 0x08000000» зависает**  
   Образ приложения под бутлоадер собран для загрузки с **0x0800800**. Если в Cube Programmer при ручной загрузке .bin указать адрес **0x08000000**, прошивка попадёт не туда — после сброса устройство зависает. **Всегда** указывайте **Start address: 0x0800800** при загрузке .bin приложения (AppBoot). При загрузке ELF программатор подставляет адреса из образа сам.  
   На платах с **STM32F030CC** (256 КБ Flash) в конфигурации AppBoot должен быть макрос **STM32F030xC** (не STM32F030x8).

9. **Прошивка от AppBoot не работает: не моргает светодиод, устройство не в сети**  
   Часто это значит, что **работает только бутлоадер**: по адресу **0x0800800** нет валидного приложения. Бутлоадер после сброса проверяет по 0x0800800 начальный SP (должен быть 0x2000xxxx) и адрес Reset (0x0800xxxx); если там 0xFFFFFFFF или мусор, он не переходит в приложение и остаётся в режиме приёма прошивки по Modbus (без моргания LED и без сети).  
   **Что сделать:** в дампе Flash проверьте адрес **0x0800800**: первые два слова — начальный SP и адрес Reset_Handler приложения. Если 0xFF или явно не из образа приложения — прошейте образ приложения (AppBoot) **по адресу 0x0800800** (в Cube Programmer: загрузка .bin, **Start address: 0x0800800**). Не стирайте весь чип и не прошивайте приложение по 0x08000000 (там должны остаться векторы и код бутлоадера). После успешной записи приложения по 0x0800800 через 120 с без активности по UART бутлоадер сам перейдёт в приложение, либо перезагрузите устройство.

10. **Прошивальщик (по аналогии с wb_flasher) не находит устройство**  
   Проверьте по пунктам:  
   - **COM-порт:** выбран правильный порт (USB‑RS485 или встроенный COM), драйвер установлен, порт не занят другой программой.  
   - **Параметры бутлоадера:** в режиме бутлоадера устройство отвечает на **115200 8N1**, адрес Modbus всегда **247**; бутлоадер **не отвечает на широковещательный адрес 0**.  
   - **Сканирование:** прошивальщик перебирает адреса 1–247 и скорости 9600, 19200, 38400, 115200. Сначала для каждого адреса запрашивается чтение регистра **290** (12 регистров — сигнатура в бутлоадере); при ответе устройство считается найденным в режиме бутлоадера. Если ответа нет — запрашиваются регистры **270–271** (серийный номер приложения); при ответе устройство считается в режиме приложения. Если устройство в приложении работает на скорости, не входящей в этот список, добавьте её в список скоростей сканирования (в проекте: `flasher_windows/scanner.py`, `SCAN_BAUDRATES`).  
   - **Проводка RS-485:** A/B не перепутаны, при необходимости терминатор 120 Ом на конце линии, общая земля при связи с USB‑адаптером.  
   - **Питание и бутлоадер:** устройство под питанием, бутлоадер один раз прошит через ST-Link (векторы 0x08000000, код 0x08038000). Если по 0x0800800 нет приложения, после сброса устройство остаётся в бутлоадере и отвечает на адрес **247** на **115200 8N1**.
   - **Переход в бутлоадер для прошивки:** запись **1** в holding-регистр **129** выполняется в контексте **приложения** (на той скорости и адресе, на которых устройство было найдено при сканировании). После этого устройство перезагружается; в течение 2 с переключите обмен на **115200 8N1**, адрес **247**, и далее работайте с регистрами 0x1000 (info), 0x2000 (data).

11. **При работе прошивальщика в лог на PB6 не появляются строки `[BL] rx ...`, `[BL] info ok ...` и т.д.**  
   Логи протокола выводятся только при **приёме кадров** (n ≥ 8). Если видите только `[BL] 6 main loop` и ничего нового при запуске прошивальщика:
   - Убедитесь, что прошита **актуальная** сборка бутлоадера с логами: выполните **полную пересборку** (`make -C bootloader clean all`) и снова прошейте объединённый образ (или только бутлоадер), затем повторите попытку.
   - Проверьте, что **прошивальщик подключён к тому же устройству**, с которого снимаете лог: терминал — на **PB6** этого устройства, прошивальщик — на **Modbus/RS-485 (PA2/PA3)** этого же устройства. Если прошивальщик на другом COM (другая плата) — кадры не придут, логов не будет.
   - При **BL_DEBUG** каждые **10 с** выводится `[BL] alive` — если оно появляется после `[BL] 6 main loop`, цикл работает и прошита версия с логами; отсутствие `[BL] rx ...` значит, что по Modbus-UART кадры не принимаются (порт, скорость, проводка).

## 8. cyntron-dtv: первая прошивка и обновление по Modbus

Для продукта **cyntron-dtv** (датчик температуры/влажности) используется та же схема Flash, что и для MP-02m: бутлоадер — общий образ из `shared/bootloader` (векторы 0x08000000, код 0x08038000); приложение под бутлоадер — 188 КБ @ 0x0800800 (линкер `STM32F030CCTX_FLASH_boot_188K.ld`, макросы BOOTLOADED, APP_FLASH_188K).

### 8.1 Первая прошивка (устройство без бутлоадера)

1. **Прошить бутлоадер** — так же, как для MP-02m (п. 3): собрать `make -C shared/bootloader -j` (или `make bootloader` из корня), загрузить образ бутлоадера через ST-Link по 0x08000000 и 0x08038000.
2. **Прошить приложение cyntron-dtv:** собрать `make -C cyntron-dtv BUILD_CFG=AppBoot`, получить `cyntron-dtv/build/AppBoot/rtu-sensor.bin`. Записать этот .bin **по адресу 0x0800800** (STM32CubeProgrammer / OpenOCD: Start address 0x0800800).
3. **Либо одной прошивкой:** собрать объединённый образ `make -C cyntron-dtv combined` → `cyntron-dtv/build/AppBoot/boot_fw_cyntron.bin` (256 КБ). Прошить его по **0x08000000** — в устройство попадут бутлоадер и AppBoot cyntron-dtv.

### 8.2 Обновление прошивки по Modbus

1. Собрать приложение: `make -C cyntron-dtv BUILD_CFG=AppBoot`.
2. Сформировать .fw (сигнатура — как в EEPROM устройства, см. п. 5):  
   `python mk/merge_combined.py` не создаёт .fw; используйте скрипт из `shared/bootloader` или аналог make_fw для образа `cyntron-dtv/build/AppBoot/rtu-sensor.elf` с нужной сигнатурой.
3. Перевести устройство в бутлоадер: записать **1** в holding-регистр **129** (как для MP-02m).
4. В течение **120 с** выполнить прошивку утилитой (flasher_windows, wb-mcu-fw-flasher и т.д.): тот же протокол, адрес бутлоадера **247**, **115200 8N1**.

Итог: первая прошивка — ST-Link (бутлоадер + AppBoot или один boot_fw_cyntron.bin); обновление по Modbus — регистр 129, .fw файл, как в п. 4 и в doc/BOOTLOADER_TZ.md.
