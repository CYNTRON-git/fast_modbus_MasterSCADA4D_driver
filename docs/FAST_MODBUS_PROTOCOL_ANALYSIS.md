## 1. Общее: адрес 0xFD и функция 0x46

| Требование | Проект | Статус |
|------------|--------|--------|
| Расширенные команды по адресу **0xFD** (не 0) | Вход в Fast Modbus по `buf[0] == 0xFD` в `modbus_rtu_hw.c` и `fast_mb.c` | ✅ |
| Команда расширенных функций **0x46** (0x60 deprecated) | Проверка `buf[1] == 0x60 \|\| buf[1] == 0x46`, ответы с той же функцией (0x46 или 0x60) | ✅ |
| CRC как в Modbus RTU | CRC по 3 байтам для 0x01/0x02, порядок байт CRC в кадре корректен | ✅ |

## 2. Сканирование шины (0x01, 0x02, 0x03, 0x04)

| Элемент | Документ | Реализация | Статус |
|---------|----------|------------|--------|
| Начало сканирования | Субкоманда **0x01**, FD 46 01 + CRC | `fast_mb.c`: case 0x01, CRC по buf[0..2] | ✅ |
| Продолжение сканирования | Субкоманда **0x02**, FD 46 02 + CRC | case 0x02 | ✅ |
| Ответ на сканирование | Субкоманда **0x03**, FD 46 03 + serial (4 байта BE) + modbus_addr + CRC | `answer_scan()`: put_1(0xFD), put_1(0x46/0x60), put_1(0x03), put_2(serial>>16), put_2(serial&0xFFFF), put_1(address_rtu) | ✅ |
| Конец сканирования | Субкоманда **0x04**, FD 46 04 + CRC | `end_scan()`: 0xFD, 0x46/0x60, 0x04 + send_msg | ✅ |
| Арбитраж: 32 окна, 4 бита приоритета + 28 бит serial | Документ и Хабр | `make_arbitrage_data()`: (0x6<<28)\|(serial&0x0FFFFFFF) неотсканированные, (0xF<<28)\|(serial&0x0FFFFFFF) отсканированные | ✅ |
| Серийный номер DIY | 0x0D000000–0x0D00FFFF | В коде не проверяется; при необходимости проверять при инициализации | ⚠️ по желанию |

## 3. Работа по серийному номеру (0x08, 0x09)

| Элемент | Документ | Реализация | Статус |
|---------|----------|------------|--------|
| Запрос к устройству по serial | FD 46 **0x08** + 4 байта serial (BE) + PDU стандартной функции + CRC | `check_fast_modbus()` case 0x08, сравнение с `fastmodbus_address`; затем `handle_emulate_standart()` в modbus.c | ✅ |
| Ответ на 0x08 | FD 46 **0x09** + 4 байта serial (BE) + тело ответа + CRC | В modbus.c ответ формируется через общий механизм ответа (put_1(0x09) и т.д. в эмуляции) | ✅ |
| Игнорирование запроса не своему serial | — | `nmbs->msg.ignored = true` при received_address != fastmodbus_address | ✅ |
| Запрет вложенного 0x46/0x60 | — | `handle_req_fc`: при fc==0x46/0x60 возврат NMBS_ERROR_INVALID_REQUEST | ✅ |
| CRC пакета 0x08 | — | Проверка CRC после приёма в handle_emulate_standart (buf_rec >= 7) | ✅ |

## 4. События: запрос и ответы (0x10, 0x11, 0x12)

Документ:
- **0x10** — запрос событий (мастер): FD 46 **0x10** + min_slave_id + max_data_len + confirm_slave_id + confirm_flag + CRC.
- **0x11** — передача событий (слейв): **slave_id** 46 **0x11** + flag + event_count + data_len + события + CRC.
- **0x12** — событий нет: FD 46 **0x12** + CRC.

В проекте:
- Распознаётся субкоманда **0x05** как «опрос событий», а не **0x10**.
- Ответ с событиями: в `answer_events()` формируется пакет с третьим байтом **0x05** и форматом, отличным от 0x11.
- При отсутствии событий ответ **0x12** не отправляется (просто не отвечаем при event_count==0).

| Элемент | Документ | Реализация | Статус |
|---------|----------|------------|--------|
| Субкоманда запроса событий | **0x10** | case **0x10** в `check_fast_modbus`, **10 байт** (8 данных + CRC), CRC по **8 байтам** (FD 46 10 min max confirm_id confirm_flag) | ✅ |
| Поля запроса 0x10 | min_id, max_len, confirm_id, confirm_flag | confirm_id/confirm_flag = buf[6], buf[7]; CRC по buf[0..7], CRC в buf[8], buf[9] | ✅ |
| Субкоманда ответа «есть события» | **0x11** | answer_events() формирует 0x11 | ✅ |
| Первый байт ответа с событиями | **slave_id** | packet[0] = address_rtu | ✅ |
| Формат события в 0x11 | (1) len_payload, (1) type, (2) id BE, (0+) payload LE | Реализовано; типы 1–4 по документу | ✅ |
| Флаг подтверждения в 0x11 | 0/1, инверсия | s_event_sent_flag, чередование; подтверждение по 0x10 | ✅ |
| Ответ «событий нет» | **0x12**: FD 46 12 + CRC | send_no_events() при event_count==0 | ✅ |
| Арбитраж событий | приоритет выше при наличии событий | priority = has_events ? 0x6 : 0xF | ✅ |

Итог: обработка событий приведена к протоколу WB (0x10/0x11/0x12), совместима с мастерами Wiren Board.

## 5. Настройка отправки событий (0x18)

Документ: команда на устройство по **slave_id**: addr 46 **0x18** + длина + список настроек (тип регистра, адрес, кол-во, приоритеты по регистрам) + CRC. Ответ с битовыми масками разрешений.

В проекте: обработки субкоманды **0x18** нет (ни в fast_mb.c, ни в modbus.c).

| Элемент | Статус |
|---------|--------|
| Приём и разбор 0x18 | ❌ не реализовано |
| Ответ на 0x18 | ❌ не реализовано |

Без 0x18 мастер не может включить/настроить события по протоколу Wiren Board.

## 6. Тайминги арбитража

Документ:
- Ожидание начала арбитража: max(3.5 символа, 12 бит + 800 мкс), не менее 800 мкс.
- Длительность арбитражного окна: 12 бит (UART-фрейм) + 50 мкс, кратно биту.

В проекте (`tim.c`, комментарии и режимы):
- Режим 1: «begin arbitrage max(3 symbols, (12 bits + 800us)) для новой 0x46» — Period = Arbitrage_Period.
- Режим 2: «arbitrage windows для новой 0x46» — Window_Period.
- Режимы 3–4: старый 0x60 (44 бита, 20 бит на окно).

Расчёт периодов (Arbitrage_Period, Window_Period) выполняется в `compute_timer()` (вызывается из fast_mb_port); без проверки конкретных формул из документа полное соответствие не подтверждено, но разделение «ожидание начала» / «окно» для 0x46 есть.

| Элемент | Статус |
|---------|--------|
| Отдельные тайминги для 0x46 и 0x60 | ✅ |
| Соответствие формулам doc (max(3.5 symbols, 12 bits+800us), 12 bits+50us) | ⚠️ нужно сверять compute_timer() с формулой |

## 7. Бутлоадер и wb-mcu-fw-flasher

По [wb-mcu-fw-flasher](https://github.com/wirenboard/wb-mcu-fw-flasher):
- Переход в бутлоадер: запись 1 в holding **129 (0x81)** — с параметрами 9600 8N2; или в **131 (0x83)** — с сохранением текущих параметров (загрузчик ≥1.3.0).
- Прошивка: Modbus RTU, команды 0x06/0x10, регистры 0x1000 (info), 0x2000 (data) и т.д.
- Адрес в бутлоадере: как в EEPROM или 0 для единственного устройства.

В проекте:
- В `modbus_rtu_hw.c` и `fast_mb.c` есть упоминания broadcast и 0x10 (Write Multiple Registers), в т.ч. для логирования «bootloader» (0x1000, 16 рег.).
- Обработка записи в регистры 129/131 и переход в бутлоадер выполняются в основном приложении (флаги/рестарт); сам бутлоадер — отдельный образ.

Вывод: интеграция с flasher ожидаемо реализуется на стороне приложения (рег. 129/131) и бутлоадера; в коде видна осведомлённость о 0x10 и 0x1000. Детальная проверка регистров бутлоадера не входила в задачу; при необходимости её нужно сверять с README репозитория wb-mcu-fw-flasher.

## 9. Внесённые исправления (реализовано)

1. **Запрос событий** — субкоманда **0x10**: распознаётся в `check_fast_modbus`, требуется 8 байт, CRC по 6 байтам, в `msg` сохраняются `event_confirm_slave_id` и `event_confirm_flag` из запроса. В IRQ вызывается `check_fast_modbus(nmbs, 0)` при любом числе байт; для 0x10 возврат только при `buf_rec >= 8`.

2. **Ответ 0x11** — первый байт **slave_id** (address_rtu), затем 0x46/0x60, 0x11, флаг (чередование 0/1), количество событий, длина поля данных, события в формате: (1) длина payload, (1) тип по документу (1=coil, 2=discrete, 3=holding, 4=input), (2) id BE, payload LE. Подтверждение: при совпадении confirm_slave_id/confirm_flag с последним отправленным пакетом вызывается `fast_mb_events_acknowledge(last_sent_count)`.

3. **Ответ 0x12** — при выигрыше арбитража и пустой очереди отправляется FD 46 12 + CRC (`send_no_events()`).

4. **Арбитраж событий** — при наличии событий приоритет 0x6, при отсутствии 0xF (`make_arbitrage_data_events` использует `fast_mb_events_has_events()`).

5. **0x18** — не реализовано; при необходимости добавить приём по slave_id и ответ с битовыми масками.

События по протоколу WB (0x10/0x11/0x12) реализованы и совместимы с [protocol.ru.md](https://github.com/wirenboard/wb-modbus-ext-scanner/blob/main/docs/protocol.ru.md). Формат и CRC запроса 0x10 приведены в соответствие с документом (10 байт кадр, CRC по 8 байтам, confirm в байтах 6–7); см. также MODBUS_AND_FAST_MODBUS_COMPLIANCE.md.
